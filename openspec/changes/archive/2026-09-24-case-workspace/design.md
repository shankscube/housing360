## Context

`cases-screen` (archived) built the Case Operations Center list/KPI/search screen and a 7-tab case detail shell against a minimal `Case` row (`id`, `clientId`, `programEnrollmentId`, `caseNumber`, `subject`, `status`, `priority`, `lastContactDate`, `assignedCaseManagerId`). Overview, Assessments, and HUD Data have real panels; Plan, Services, Referrals, and Health and Wellness render `NotYetBuiltPanel`, and `GET /api/cases/:id`'s `tabsWithContent` reports `false` for all four because no backing table exists yet (see that change's design.md, Decision 2). There is also no case-create UI (only a derive-enrollment-from-client `POST /api/cases` with no Subject requirement) and no case-edit UI.

This change fills every one of those gaps by extending `Case` in place and adding the tables/endpoints/panels each tab needs, following the same layering (`routes/ → controllers/ → services/ → models/`, `sendSuccess`/`sendError` responder, HUD-coded scalars as plain Strings resolved against a constants map, no Prisma enum for anything HUD-adjacent) and frontend conventions (`apps/web` owns all UI, one Redux slice per domain, thunks through `api/client.ts`) established across `client-management`, `client-intake`, and `case-management`.

**Scale note**: this is the largest single change in the repo so far — 16 new Prisma models plus extensions to 2 existing ones, ~30 new endpoints, 4 full tab UIs plus a header/Edit form plus a shared ROI component. `tasks.md` groups work by tab specifically so each tab can be implemented, migrated, and manually verified independently rather than as one atomic drop.

## Goals / Non-Goals

**Goals:**
- Extend `Case`/`InteractionSummary` in place; every new table links back to `Case`, `Client`, or `ProgramEnrollment` via a real FK, never a parallel identifier.
- Give every one of the 6 non-Overview tabs real, data-backed content, replacing `NotYetBuiltPanel` for Plan, Services, Referrals, and Health and Wellness (Assessments already has a real panel from `cases-screen`; this change only adds its enrollment picker and Recommended Care Plans strip).
- Introduce exactly the shared primitives this change actually needs twice or more (`Modal`, `ExpandableRow`, `SignaturePad`) into `apps/web/src/components/ui/`, per the standing rule against a `packages/ui` split.
- Keep every tab's empty state a labeled empty state, never an error, per `case-management`'s existing "no fabricated data" requirement.
- Make the ROI legal text and the Care Plan wizard's suggested-goal catalog config-driven (constants/seed data), not hardcoded in components, mirroring `hudOptions.ts`'s role.

**Non-Goals:**
- The Entry Assessment scoring engine or a second assessment stage — Assessments tab's "New"/"Resume Draft" continue to route to a documented placeholder (Phase 5b).
- A real EHR integration — `EhrAdapter` ships as a no-op only; `clinical_summaries`/`clinical_encounters` are a read model with no writer in this change.
- Shelter Management's full bed/unit management (multi-unit, capacity rules, waitlists) — `beds`/`bed_assignments`/`bed_nights` are intentionally minimal, scoped to what the Services tab's "Assign Bed" + Daily Log needs.
- A case status/priority/stage state machine, approval workflow, or audit trail beyond `createdAt`/`updatedAt` — fields stay plain, matching `case-management`'s existing precedent.
- Role-based authorization beyond the existing single-demo-user `requireAuth` gate — "Case Manager" pickers list all `User` rows, same as `case-management`'s read-only case-manager display.

## Decisions

### 1. `Case` gains 15 new columns in place; no `CaseDetail` split table
New nullable/defaulted columns on `Case`: `description` (Text), `stage` (String, HUD-coded-scalar convention, resolved against a new `constants` map), `origin` (String, same convention), `escalated` (Boolean, default `false`), `contact` (String, free text — the modal's "Contact" field has no dedicated sub-shape in the prompt, so it's a single free-text line, matching how `subject` is already free text), `referralId` (String?, FK to the new `Referral`), `openedDate` (DateTime, defaults to `now()` at creation), `closedAt` (DateTime?), `nextHmisReviewDue` (DateTime?), `hmisDataQualityStatus` (String?, HUD-coded-scalar convention), `followUpMilestone` (String, enum-like but plain String: `none | 30 | 60 | 90`, default `none`), `followUpDueDate` (DateTime?), `createdById` (Int?, FK `User`), `updatedById` (Int?, FK `User`). `caseNumber`/`clientId`/`programEnrollmentId`/`status`/`priority`/`lastContactDate`/`assignedCaseManagerId` are unchanged. `@@unique([clientId, programEnrollmentId])` and `cases/ensure`'s upsert contract are untouched — `ensureCase` continues to only set `status: 'open'` on first insert; every new column defaults or stays null until the case-manager UI (New Case, Edit, Follow-Up Reminder) writes it.

`createdById`/`updatedById` back the Overview tab's System Information block ("created/modified by and on" — the "on" half is the existing `createdAt`/`updatedAt`). `createdById` is set once, from `req.user.id`, at `POST /api/cases` (never at `cases/ensure`'s intake-time upsert, which has no case-manager UI context — those cases keep `createdById: null`, rendered as "System" in System Information). `updatedById` is set from `req.user.id` on every `PATCH /api/cases/:id` and `PATCH /api/cases/:id/follow-up` call.

**Alternative considered**: a 1:1 `CaseExtended` table. Rejected for the same reason `cases-screen` rejected it originally — no isolation benefit, and every new field here is read on the same request (`GET /api/cases/:id`) that already reads `Case`.

### 2. `followUpDueDate` is computed server-side at write time, not derived at read time
Unlike the HUD Data checklist (computed at request time on purpose, since its inputs change under it), the Follow-Up Reminder's due date is a **decision made at the moment it's set** — "30 Day" means 30 days from *now* (or from `lastContactDate` if the prompt's later behavior requires that baseline; confirmed via the spec scenario "60 Day follow-up stores ... a due date 60 days out" — baseline is the moment the reminder is set, i.e. `now()`, not `openedDate`, since `openedDate` could be arbitrarily old and would make "60 days out" meaningless as a reminder). `PATCH /api/cases/:id/follow-up { milestone }` computes `followUpDueDate = milestone === 'none' ? null : addDays(now(), milestone)` and stores both columns; a later read never recomputes it. Setting `milestone: 'none'` clears both columns to `null`.

**Alternative considered**: compute from `lastContactDate`. Rejected — `lastContactDate` can be null (case never contacted) or stale by design (it's a manually-set field elsewhere in the Overview tab), and the prompt's own data-model line lists `opened_date or last contact` as alternatives without picking one; "the instant the reminder is set" is the only baseline that always exists and matches ordinary reminder-setting UX (the bundle's "Set Reminder" button, not an ambient recalculation).

### 3. One shared `Task` table, not a per-feature tasks table
`Task { id, subject, description?, status, priority?, subtype?, dueDate?, ownerId (FK User), clientId (FK Client), caseId? (FK Case), goalAssignmentId? (FK GoalAssignment), interactionSummaryId? (FK InteractionSummary), createdAt, updatedAt }`. `status`/`priority`/`subtype` are plain Strings (HUD-coded-scalar convention applies broadly in this repo, and `subtype` in particular distinguishes a plain case task from a care-plan-goal task from a follow-up task without a second table). Every writer (Overview's Tasks card, a care-plan goal's task list, an interaction summary's optional "Create a Task" block) inserts through one `task.service.ts`; every reader filters by whichever FK is non-null for its view (`GET /api/cases/:id/tasks` filters `caseId`, a goal's task list filters `goalAssignmentId`). This is also what makes the proposal's "Home, Tasks, and Client 360 all read this table later" true without a future migration.

**Alternative considered**: a `CaseTask` table plus a separate `GoalTask` table. Rejected — identical shape, and the prompt explicitly calls for one table; splitting would force two read paths for what's conceptually one "is there anything to do" list.

### 4. Care plans: template catalog is seed data, not a builder UI
`CarePlanTemplate`/its nested template-goal/template-task rows are **not** editable through this change's UI — no "create a template" screen exists. They're seeded (`prisma/seed.ts`, extending the existing seed script) the same way `Program` is seeded and not user-creatable. `GoalDefinition` (the suggested-goal catalog used both standalone in the wizard's Goals step and as what a template's goals reference) is seeded the same way. `POST /api/care-plans` accepts either `templateId` (clone the template's goals/tasks as starting `GoalAssignment`/`Task` rows, still editable after) or a blank plan; either way, the wizard's own Goals/Tasks steps are what the case manager actually edits before saving — the clone is a starting point, not a live link back to the template.

**Alternative considered**: let templates be case-manager-editable. Rejected — out of scope per the prompt (no "manage templates" screen is specified anywhere in the Frontend section), and conflating "template management" with "using a template" would blow up this change's already-large surface.

### 5. Care Plan wizard: one transaction, client-side-then-server-side validation, not a draft-row pattern
`POST /api/care-plans` takes the whole plan shape (`{ name, description, status, startDate, endDate, templateId?, goals: [{ name, description, priority, serviceDomain, goalDefinitionId?, tasks: [{ subject, dueDate? }] }] }`) and writes plan + all goals + all tasks inside one Prisma `$transaction`, mirroring `households/:id/members`'s existing bulk-write-in-one-transaction precedent. The wizard's per-step validation ("Give every goal a name...", "Give every task a subject...") is enforced client-side before the final submit (steps 2 and 3 block their own "Next"/"Save" the same way the intake wizard's steps block advancing), and the server re-validates the same two rules before writing (empty-name goal or empty-subject task in the payload → 400, never a partial write) — belt-and-suspenders, consistent with `client-intake`'s pattern of client-side gating plus a server that never trusts it blindly. **No draft is persisted between wizard steps** — unlike the intake wizard (which persists per-step because a case manager might abandon and resume across sessions), the Care Plan wizard's state lives in React state only until the final "Save"/"Create" action, because there is no cross-session resume requirement in the prompt and partial care plans have no meaning on their own (a plan with a name but no goals isn't useful to show elsewhere in the app before it's finished).
Editing an existing plan (add a goal, edit one goal) reuses the same wizard component pre-filled and calls `PATCH /api/care-plans/:id` (plan fields) / `POST /api/care-plans/:id/goals` (append) / `PATCH /api/goal-assignments/:id` (edit one) rather than re-running the full create transaction.

**Alternative considered**: autosave each wizard step like the intake wizard. Rejected — care plans are short-lived to create (typically one sitting) and the prompt's validation messages ("remove the empty one, to continue") describe blocking-on-submit behavior, not per-step persistence.

### 6. Service gaps: computed at request time from `GoalAssignment.serviceDomain` vs. `Benefit.serviceDomain`, not stored

**Implementation note**: because this decision depends on `Benefit` existing, `Benefit`/`BenefitAssignment` were created in the Plan tab's migration (tasks.md Group 5) rather than Services' (Group 6) — the Migration Plan section below described one migration per tab in isolation, but this one dependency crosses that boundary. `ServiceDisbursement`/`Bed`/`BedAssignment`/`BedNight` stayed in Group 6 as planned, since only the Services tab needs those.

`GET /api/cases/:id/service-gaps` collects the distinct `serviceDomain` values across the case's active goal assignments, checks each against the set of `serviceDomain`s covered by `Benefit` rows on the client's programs (via `BenefitAssignment`... actually via `Benefit.programId` across the client's `ProgramEnrollment`s), and returns the domains with no in-house coverage — same "computed, not stored" philosophy as the HUD Data checklist (`cases-screen` Decision 4), because coverage changes whenever benefits/enrollments change and a stored flag would go stale silently.

### 7. Refer to Partner Agency: ROI consent check reuses one `roi-status` endpoint from both the Plan tab and Health & Wellness tab
`GET /api/clients/:id/roi-status` returns `{ hasActiveConsent: boolean, activeRoi: ReleaseOfInformationSummary | null }` — "active" means an unrevoked (`revokedAt IS NULL`) row with `expiresOn > now()`. Both the Plan tab's partner-referral flow (show what's authorized, or offer Create ROI / Continue Without ROI) and the Health & Wellness tab (ROI status line + Create action) call this same endpoint; there is exactly one definition of "active consent" in the codebase (a service function, `releaseOfInformation.service.ts`'s `getActiveRoi(clientId)`), never duplicated as a second date-comparison inline in a controller.
`POST /api/referrals/external` (used only by the Refer to Partner flow, distinct from the Referrals tab's `POST /api/referrals`) accepts `{ caseId, goalAssignmentId?, providerOrgId, notes? }`, looks up active consent server-side (never trusts a client-sent "hasConsent" boolean), and sets `Referral.isExternal = true` plus either full client contact fields (consent present — copied from what the ROI record authorizes) or `clientContact` reduced to initials only (no consent) — the "Continue Without ROI" checkbox is a UI confirmation gate only, not what the server relies on to decide how much data to store.

### 8. Referrals: one `Referral` table serves both the Referrals tab and the Plan tab's external-referral path
Internal Referrals-tab referrals (`POST /api/referrals`) and Plan-tab partner referrals (`POST /api/referrals/external`) write the same table, differing only in `isExternal` and which fields get populated (external referrals never populate full `clientContact` without consent, per Decision 7). The Referrals tab's list, Accept, and Decline endpoints operate on `Referral` regardless of `isExternal`, so a partner referral created from the Plan tab is visible and manageable from the Referrals tab too — one system of record, not two referral concepts. `Case.referralId` (the New Case modal's "Referral" field and the detail header's "Referral" line) is a nullable FK to this same table, letting a case originate from a referral.

### 9. Beds: `bed_assignments` has no `endDate` enforcement beyond "don't offer an already-assigned bed for that date+shift"
`GET /api/programs/:id/beds/available?date=&shift=` returns beds on that program with no `BedAssignment` covering that `date`+`shift` combination where `endDate IS NULL OR endDate >= date` — a simple overlap check, not a full calendar/capacity engine (that's Shelter Management's job later). `POST /api/bed-assignments` creates the assignment and, in the same transaction, inserts a `BedNight` row for *today* with `status: 'Present'` (per the prompt's explicit "also logs today's night as Present" and the end-to-end scenario "assigns a bed and mark two nights" — the assignment call logs the first night; the Daily Log view's one-click logging produces the rest). `PATCH /api/bed-nights/:id` supports correcting a logged night's status; `POST /api/bed-nights` supports logging a night other than today (the Daily Log calendar's one-click cells).

**Implementation note**: to make the "same bed/date/shift is not offered" exclusion actually computable, `shift` lives on `BedAssignment` itself (not only on `BedNight`) — a bed assignment is scoped to one shift (Day or Overnight) from `startDate` onward. This wasn't spelled out above but follows directly from the proposal's "Assign Bed: program, date, shift" fields; without it, two assignments to the same bed on different shifts of the same date couldn't be told apart.

### 10. Health & Wellness: `EhrAdapter` interface lives in `apps/api/src/services/`, resolved once at module load, no runtime provider switch
```ts
interface EhrAdapter {
  getClinicalSummary(clientId: string): Promise<ClinicalSummary | null>;
  listRecentEncounters(clientId: string, limit: number): Promise<ClinicalEncounter[]>;
}
```
`services/ehr/noopEhrAdapter.ts` implements it returning `null`/`[]` always.

**Correction during implementation**: this decision originally assumed `health.controller.ts`/`health.service.ts`/`health.routes.ts` were a placeholder for this domain. They're actually the app's infra `/health` liveness/readiness check (`GET /health`, unauthenticated, pings the DB) — completely unrelated to client health/wellness content, and not to be touched here. This tab's backend instead gets its own `healthWellness.service.ts`/`.controller.ts`/`.routes.ts`, importing the no-op adapter directly — same "no factory/env-var provider selection" reasoning (exactly one implementation exists; adding indirection for a hypothetical second one is the kind of speculative abstraction the repo's conventions warn against). `clinical_summaries`/`clinical_encounters` tables exist so the *shape* is real (a future change swaps in a real adapter with zero schema change), but nothing in this change ever inserts a row into them — `GET /api/clients/:id/health-wellness` always returns the adapter's empty result today, which is what renders the "No clinical data on file for this client yet." copy. No vendor name appears anywhere in `apps/web` strings, per the proposal.

### 11. ROI: one shared `ReleaseOfInformationForm` component; legal text in one config file
`apps/api/src/constants/roiDisclosureText.ts` holds the authorization text and the 42 CFR Part 2 re-disclosure notice as named string constants, served via a small addition to the existing `/api/reference` router (`GET /api/reference/roi-text`) — same pattern as `hudOptions.ts`/`HUD_WORKSPACE_DISCLOSURE_TEXT`, never inlined in the React component. `apps/web/src/components/ui/SignaturePad/` is a new generic canvas-based component (`{ value, onChange, onClear }`, no external dependency — pointer events drawn to a `<canvas>`, exported as a data URL) used twice for one ROI form (client signature, staff signature). `expiresOn` defaults server-side to `signedAt + 365 days` when the request omits it; revocation is `PATCH`-free in this change (no "revoke" UI is specified) — the schema supports `revokedAt` for future use, but nothing in this change's UI sets it.

### 12. Shared UI additions: `Modal`, `ExpandableRow` — both content-agnostic, added to `components/ui/`
- **`Modal`** (`components/ui/Modal/`): the first generic overlay/dialog primitive in the repo (the intake wizard hand-rolled its own `fixed inset-0` overlay before any other modal existed). `{ isOpen, onClose, title, children, size? }`, renders via `createPortal` to `document.body` (same technique the nav-rail account menu already uses), traps no focus beyond a basic Escape-to-close and backdrop-click-to-close. New Case, Edit Case, the Care Plan wizard, Assign Service, New/Edit Disbursement, Assign Bed, New/Edit Referral, Decline Referral, and the ROI form all render through this one component instead of each hand-rolling an overlay — this is the change that finally justifies extracting it (three-plus call sites, per the repo's own "three similar lines is better than a premature abstraction" bar being clearly exceeded here).
- **`ExpandableRow`** (`components/ui/ExpandableRow/`): a single collapsible row (`{ summary: ReactNode, children: ReactNode, defaultExpanded? }`) used for care-plan → goals → tasks nesting and enrollments → services → disbursements nesting — two independent tabs need the identical "click a row, see its children indented below" pattern, so it's built once rather than twice.
Both are screen-agnostic with typed props and no case-specific logic, so they satisfy the standing rule's bar for living in `apps/web/src/components/ui/` rather than a feature folder.

### 13. Redux: `casesSlice` gains `caseDetail`; three new slices, no cross-slice coupling
`casesSlice.ts`'s existing `detail` (the case row + `hudData` sub-state from `cases-screen`) is joined by sibling sub-state for this change's tabs — interaction summaries, tasks, and the follow-up control — rather than a separate slice, since they're all scoped to "the currently open case" the same way `hudData` already is. `carePlansSlice`, `servicesSlice`, `referralsSlice` are separate top-level slices (per the proposal) because each has its own list-fetch/create/update lifecycle independent of which case is open (e.g. `referralsSlice` also needs to support the Plan tab's partner-agency lookup, which isn't case-detail-shaped). All thunks call `apiClient` directly, same as `casesSlice`'s existing thunks — no new wrapper layer.

## Risks / Trade-offs

- [16 new tables plus 2 extended in one change] → mitigated by grouping `tasks.md` per tab so each tab's migration + endpoints + UI can be applied and manually verified in isolation before moving to the next; a failure in, say, Services doesn't block Referrals from already being verified.
- [`followUpDueDate` baseline (Decision 2) is an inference, not explicitly stated by the prompt] → flagged as an Open Question below; low blast radius since it's one `addDays` call site.
- [`contact`/`escalated` on `Case` (Decision 1) have no explicit column spec in the prompt's data-model list, only appearing as New Case modal fields] → treated as a plain String and Boolean respectively, lowest-complexity reading; flagged as an Open Question.
- [One `Referral` table serving two creation paths (Decision 8) means `POST /api/referrals` and `POST /api/referrals/external` share a model but diverge on which fields are trusted from the client] → mitigated by keeping consent-driven field population entirely server-side (Decision 7), so a modified frontend request can't force full contact details into an external referral without consent.
- [`Modal`/`ExpandableRow` are introduced mid-way through the app rather than from the start] → existing `IntakeWizard` keeps its own hand-rolled overlay (out of scope to refactor here); only new call sites in this change use `Modal`, so no regression risk to intake.
- [Care Plan wizard has no server-side draft persistence (Decision 5)] → a browser refresh mid-wizard loses in-progress goals/tasks; acceptable since the prompt describes no resume requirement for this wizard (unlike the intake wizard, which explicitly does).

## Migration Plan

1. One Prisma migration per tab group (Overview/Tasks → Plan → Services → Referrals → Health & Wellness), applied in that order, matching `tasks.md`'s grouping — keeps each migration reviewable and independently revertible during development rather than one enormous schema diff.
2. `prisma/seed.ts` gains new seed blocks (in the same run, guarded the same way existing seed blocks are) for `CarePlanTemplate`+nested rows, `GoalDefinition`, `Benefit`, `Organization`+`OrganizationServiceDomain`, and a handful of `Bed` rows per seeded `Program` — all additive, none touch the existing `User`/`Program` seed rows.
3. No backfill needed — every new column on `Case`/`InteractionSummary` is nullable or has a safe default (`escalated` false, `followUpMilestone` `'none'`, `openedDate` defaults to creation time), so existing rows remain valid without a data migration step.
4. Rollback: standard Prisma migration `down` per step; since nothing in this change deletes or renames an existing column, rollback risk is limited to the new tables/columns themselves.

## Open Questions

- Whether `followUpDueDate`'s baseline should be "now" (Decision 2's choice) or `lastContactDate` when present — confirm against the design bundle / stakeholder intent during implementation if it surfaces as wrong in review.
- Exact shape of the New Case modal's "Contact" field (Decision 1: currently a single free-text line) — the prompt names it without a sub-shape; revisit if the bundle implies a structured phone/email pair.
- Whether `Referral.category`/`outcome`/`type` need a fixed HUD-adjacent code list (via a constants map) or stay free text — deferred to implementation, defaulting to free text unless the design bundle shows a fixed dropdown vocabulary.
- Whether care plan templates ever need a management UI — explicitly out of scope here (Decision 4); flagged for a future change if seed-data-only proves insufficient in practice.

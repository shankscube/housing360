## Context

Both the Assessment Command Center and Coordinated Entry (built in the archived `assessments-and-coordinated-entry` change) run on documented placeholders. `apps/api/src/services/scoring.service.ts` is a single file whose header explicitly says "PROVISIONAL — replace when the real HUD/VI-SPDAT scoring design lands"; it exposes `scoreAssessment`/`scoreVulnerability`, both small fixed-weight tallies with no persisted breakdown. `VulnerabilityAssessment.answers` is a free-form `Json` bag "since the real instrument isn't designed yet" (that change's design.md, Decision 3). There is no stage-eligibility concept at all today — `Assessment` already has `status` (`in_progress`/`completed`, default `in_progress`), `type` (`entry`/`annual`/`exit`), `dueDate`, `score`, `scoreLabel`, and `cycleNumber` with `@@unique([programEnrollmentId, dataCollectionStage, cycleNumber])`, but nothing stops a second Entry assessment or an Annual assessment outside its window, and nothing tells the UI a draft already exists on an enrollment before it lets a case manager start a new one.

The Case detail page's Assessments tab (`apps/web/src/features/cases/panels/AssessmentsPanel.tsx`, from `case-workspace`) already lists an enrollment's assessments and has a working enrollment picker and a "Recommended Care Plans" strip, but "Resume Draft"/"New Assessment" both just show a toast ("...arrives in a later phase"), and "Discard" deletes a draft immediately with no confirmation — `case-workspace`'s own design.md flagged this as its Non-Goal, explicitly deferred to this change ("Phase 5b").

On the frontend, the client-intake wizard's steps 4-6 (`Step4LivingSituation.tsx`, `Step5IncomeBenefits.tsx`, `Step6HealthDv.tsx`) and step 7 (`Step7Disabilities.tsx`) are monolithic components with all markup inlined and directly coupled to `state.intake.*` and a module-level singleton draft store (`steps/assessmentDraft.ts`, keyed only by `clientId`, not safe for a second concurrent editing surface). No section-level presentational component exists to reuse today — extracting one is real work, not a re-import.

`GET /api/reference/hud-options` has no `destinationType`/`destination` keys — the Exit Details "Destination Type → Destination" dependent select this change needs has no HUD code source to draw on yet, unlike Living Situation's existing `situationCategory`/`situationType` pair.

`Program` has no `type`/category or organization-link column (`coordinatedEntryOptions.ts`'s own comment already flags this as a known gap), which blocks a real "score band → recommended project types → partner programs with address + live beds" chain — today's "recommended programs" is a static tier→program-name string lookup.

There is no role/permission system in this app beyond `requireAuth` + one seeded demo user (`apps/api/src/middlewares/auth.ts`) — `ce:manage-rules` needs something to check against that doesn't exist today.

## Goals / Non-Goals

**Goals:**
- Real, deterministic stage-eligibility rules for Entry/Update/Annual/Exit, in one service, with draft-forces-resume behavior.
- A real, contribution-based `HousingStabilityScoringService` (rules-table-driven, auditable) replacing the fixed-weight `scoreAssessment` placeholder, and a parallel configurable Coordinated Entry rule/scoring model replacing `scoreVulnerability`.
- Program-exit recording wired transactionally to Exit-assessment completion.
- Care-plan-template recommendations driven by real rules instead of "every published template."
- A complete Case → Assessments tab (real form + detail, not a toast) reusing the same components the Assessment Command Center uses.
- A configurable, admin-auditable Coordinated Entry question/scoring/override model, with live bed availability wired into program recommendations.
- Reuse — not duplicate — the intake wizard's Living Situation / Income & Benefits / Health & DV / Disabilities section markup, by extracting it into props-driven components.

**Non-Goals:**
- Tuning the real HUD housing-stability weights or the real VI-SPDAT-equivalent CE question bank/weights — both ship as clearly-marked provisional seed data; the *engine*, contribution/audit trail, and wiring are in scope, the *numbers* are an open item for the program team (same posture the prior change took).
- A rule-editor UI for Coordinated Entry questions/bands/overrides — this change ships the API and the `ce:manage-rules` permission check only; the editor screens are a later Admin Panel phase.
- A general-purpose role/permission management system. We add the minimum needed to gate `ce:manage-rules` (see Decision 9) — not a roles UI, not a broader ACL model.
- Confirming the exact HUD Destination (3.12) code list or Program project-type taxonomy against the source system — both ship as reasonable placeholders with an explicit open item.
- Changing how the `client-intake` wizard itself persists (its steps keep using `assessmentDraft.ts` unchanged) — only the *markup* is extracted for reuse, not the wizard's state management.

## Decisions

### 1. Reuse existing `Assessment.status` vocabulary; add only 3 new columns
The proposal's "status Draft | Complete" is a UI framing, not a new schema value: `Assessment.status` already holds `in_progress`/`completed` and every existing consumer (`assessmentDisplayStatus`, the Command Center's status filter, `AssessmentsPanel`'s draft check) depends on those exact strings. We keep the stored values unchanged and map them to "Draft"/"Complete" labels only in the UI (a `assessmentStatusLabel` helper alongside the existing `assessmentDisplayStatus`). Likewise `type`, `dueDate`, `score`, `scoreLabel`, and `cycleNumber` already exist and are reused as-is. The only genuinely new `Assessment` columns are `assessorId` (`String?`, FK to `User`), `legacySyncStatus` (`String @default("not_synced")`, values `not_synced|pending|synced|failed`), and `legacySyncDate` (`DateTime?`). **Alternative considered**: introduce a new `Draft|Complete` enum-like string and migrate existing rows — rejected, it would require touching every existing status consumer for no behavioral gain.

### 2. `AssessmentEligibilityService` is a single new service, no schema change beyond reads
Given a `programEnrollmentId`, it queries existing `Assessment` rows (by `dataCollectionStage`/`status`/`assessmentDate`) and `ProgramEnrollment.startDate`, and returns `{ stage, allowed, reason, draftAssessmentId? }[]` for all four stages, implementing exactly the HUD-standard rules from the proposal (one Entry ever, Update any time between Entry and Exit, Annual only within ±30 days of each start-date anniversary and once per window, Exit once while active). This is the one place these rules live — controllers call it, never re-derive eligibility inline. **Open item** (carried forward, same posture as the prior change's stage-mapping caveat): confirm these HUD-standard rules against the source org — the exact rules were not visible during this design pass.

### 3. Program exits: new `program_exits` table, transactional with Exit-assessment completion
`program_exits(id, programEnrollmentId, assessmentId, exitDate, destinationType, destination, caseManagerExitReason, createdAt)`. `assessment.service.ts`'s completion path, when `dataCollectionStage === 3` (Exit) and the resulting `status` is `completed`, creates the `program_exits` row and updates `ProgramEnrollment.status`/adds `ProgramEnrollment.endDate` (new nullable column — `ProgramEnrollment` has no exit-related field today) in the same Prisma transaction as the assessment write and scoring. Destination Type/Destination reuse the same two-level HUD-code-map pattern as `situationCategory`/`situationType`: we add `destinationType`/`destination` keys to `hudOptions.ts`, seeded with the standard HUD 3.12 Destination taxonomy. **Open item**: confirm the exact Destination code list against the source org — no prior art exists in this repo for it (unlike Living Situation).

### 4. Scoring: `scoring_rules` + `assessment_score_contributions`, and `scoring.service.ts` is replaced, not extended
`scoring_rules(id, field, matchValue, rangeMin, rangeMax, contribution, isActive)` — one row per scoring factor, seeded with a clearly-marked-provisional rule set mirroring the old fixed-weight tally's factors (chronic homelessness, months homeless, income presence, DV survivor, disability count) so behavior doesn't regress, just becomes data-driven and auditable. `HousingStabilityScoringService.score(assessment)` evaluates active rules against the assessment's field values, writes one `assessment_score_contributions` row per matching rule (`assessmentId, field, value, contribution`), sums contributions into `score`, and derives `scoreLabel` from the same band cutoffs the placeholder used (documented as provisional, not clinical). The old `apps/api/src/services/scoring.service.ts` file and its `ScoringService` interface are deleted, not deprecated in place — nothing outside `assessment.service.ts` and the coordinated-entry code called it, and the repo's own convention is to delete rather than leave a backward-compat shim once something is genuinely unused. `assessment.service.ts`'s `scoreIfCompleted()` calls the new service instead.

### 5. Care-plan-template recommendations: `care_plan_template_rules` replaces "every published template"
`care_plan_template_rules(id, templateId, scoreBandMin, scoreBandMax, fieldCondition?, priority)` — evaluated by `carePlan.service.ts`'s `getRecommendedCarePlanTemplates(enrollmentId)` against the enrollment's latest completed assessment's score/fields, ordered by `priority`, falling back to today's "all published templates" behavior only if no rule matches (so an enrollment with no scored assessment yet doesn't see an empty strip).

### 6. Coordinated Entry: new config + assessment tables replace `VulnerabilityAssessment.answers`
New tables per the proposal: `ce_questions`, `ce_answer_options`, `ce_score_bands`, `ce_flag_overrides`, `ce_rule_changes` (audit), `ce_assessments`, `ce_responses`. **BREAKING, deliberately**: `VulnerabilityAssessment` is dropped entirely rather than kept alongside the new tables — this is a demo app with one seeded user and no real production data, so there is nothing to migrate, and keeping both would mean two parallel "vulnerability assessment" concepts (violates the "no backwards-compat shims" standing rule). `ce_assessments` takes over `VulnerabilityAssessment`'s role including the `referralId` unique FK link to `Referral`, and `Referral.originatingVulnerabilityAssessment` becomes `Referral.originatingCeAssessment`. `CoordinatedEntryService.score(responses[])` sums the chosen `ce_answer_options.score` values, finds the `ce_score_bands` row whose `[minScore, maxScore]` contains the total (inclusive at both ends), and applies `ce_flag_overrides` in a fixed evaluation order (Safety Alert → Veteran → Unaccompanied Youth) so a `replace` override is deterministic when more than one flag is set: each `replace` override, if triggered, replaces the working recommended-project-types list (last `replace` wins in evaluation order); each `add` override appends to whatever the working list is at that point. A triggered Safety Alert override additionally sets `referralSuppressed: true` on the service's return value and carries its `externalReferralMessage` through untouched. **Alternative considered**: let the caller merge multiple overrides itself — rejected, "override evaluation order" needs to live in one place (the service) so the UI's "override applied" markers and the actual recommendation never disagree.

### 7. Program gains `projectTypeCode` and `operatingOrganizationId` (new, minimal)
`ce_score_bands.recommended_project_type_codes` needs something to filter `Program` rows by, and the Partner Agencies step needs each program's address (via its operating organization) and live bed count — neither exists on `Program` today. We add two nullable columns: `projectTypeCode` (`String?`, HUD 2.02 Project Type code) and `operatingOrganizationId` (`String?`, FK to `Organization`), and backfill the 5 seeded programs in `prisma/seed.ts`. `GET /api/ce/recommended-programs?projectType=` filters on `projectTypeCode` and joins the operating organization for address plus a live `Bed`/`BedAssignment` count for availability. **Open item**: confirm the real HUD project-type taxonomy and correct organization linkage for the 5 seeded programs against the source org — this design seeds reasonable placeholder values, same posture as the Destination codes above.

### 8. `ce:manage-rules` permission: minimal role column + a small permission-check middleware, not a roles system
We add `User.role` (`String @default("case_manager")`) and one `ROLE_PERMISSIONS: Record<string, string[]>` map in `apps/api/src/constants/` (e.g. `admin -> ['ce:manage-rules']`, `case_manager -> []`). A `requirePermission(permission)` middleware (alongside `requireAuth` in `middlewares/`) 403s when the current user's role doesn't grant it, and every write on the rule-admin routes goes through it and then writes a `ce_rule_changes` row (before/after JSON, actor, timestamp) in the same transaction. `prisma/seed.ts` gains an optional `SEED_USER_ROLE` env var (default `case_manager`, so existing demo behavior is unchanged unless explicitly configured to `admin`). **Alternative considered**: hardcode the check to always-allow with a `// TODO: real RBAC` comment — rejected; the proposal explicitly asked for a real permission check, and a single role column is small enough not to count as over-building a roles system (no role-management UI, no multi-role-per-user, no scoped resource permissions).

### 9. Frontend: extract reusable section components into `apps/web/src/components/ui/`
`LivingSituationSection`, `IncomeBenefitsSection`, `HealthDvSection`, and `DisabilitiesEditor` are extracted from `Step4LivingSituation.tsx`/`Step5IncomeBenefits.tsx`/`Step6HealthDv.tsx`/`Step7Disabilities.tsx` into pure, props-driven components under `apps/web/src/components/ui/` (values, onChange, hudOptions in; no Redux, no direct API calls) — per the standing rule that generic, screen-agnostic pieces live there, and per this change's explicit instruction to put shared components there rather than under a feature folder. The wizard's existing steps become thin wrappers that pass `useAssessmentDraft()` state into these components' props (zero behavior change to the shipped wizard); the new Assessment form modal (Command Center + Case tab) wraps the same components with its **own** local form state (a small `useAssessmentFormDraft` hook), not the module-level `assessmentDraft.ts` singleton — the research for this change found that singleton is keyed only by `clientId` with no instance isolation, so a second concurrent editing surface (a modal opened while the wizard is also open) would collide. `DisabilitiesEditor` is pure list-state (add/remove rows in memory); the new modal saves the whole set via the new `PUT /api/assessments/:id/disabilities` (replace-in-one-call) endpoint, while the wizard's step 7 keeps its existing per-row add/remove thunks unchanged (no reason to touch already-shipped, working persistence). `GatedField` (already fully generic) is reused as-is by all four sections' Yes/No-gated fields.

### 10. Confirm-dialog primitive: new `ConfirmDialog`, built on the existing `Modal`
No confirm/alert primitive exists anywhere in the repo today (`AssessmentsPanel`'s current "Discard" deletes immediately with no confirmation). We add `apps/web/src/components/ui/ConfirmDialog/` as a thin, generic composition over the existing `Modal` (title, message, confirm/cancel labels, danger styling) and use it for every "Discard Draft" action this change adds (Command Center, Case Assessments tab) — replacing `AssessmentsPanel`'s immediate-delete with a real confirmation, and giving future features a primitive to reuse instead of another one-off.

### 11. Two different existing modal patterns, reused as-is for two different flows
The 3-step "Launch Assessment" modal follows the precedent already set by `features/cases/plan/CarePlanWizard.tsx`: one `Modal` + local `step` state + a plain "Step N of 3" text indicator + per-step Next/Cancel validation — not `StatusStepper` (research confirmed `CarePlanWizard` itself doesn't use it; introducing a visual stepper here would be a new pattern for a 3-step *launch* flow that doesn't need one). The Coordinated Entry workflow, by contrast, already uses `StatusStepper` exactly this way in the existing `CoordinatedEntryWizard.tsx` (a static 4-stage array + locally-owned `currentStep`) — we keep that pattern unchanged and only swap Step 1's internals (see Decision 12).

### 12. Vulnerability Assessment modal becomes config-driven, wizard shell untouched
`Step1VulnerabilityAssessment.tsx`'s fixed placeholder checkboxes/number fields are replaced with a renderer over `GET /api/ce/questions` (active, ordered) plus the three fixed intake flags (Veteran, Unaccompanied Youth, Safety Alert — kept as real checkboxes, not config rows, matching the proposal's explicit split between "intake flags" and "active questions"). Nothing about question text/answer options/scores is hardcoded in the component. The step's external contract (`onComplete`) is unchanged, so `CoordinatedEntryWizard.tsx`/`StatusStepper` wiring needs no changes.

### 13. Priority queue filter becomes single-select, a deliberate break from the existing composable model
The existing `coordinated-entry` spec's "Prioritization List Quick Filters Compose" requirement makes the five quick filters independently toggleable and AND-composed. This change's own API shape (`GET /api/ce/priority-queue?filter=TOP5|VETERAN|YOUTH|SAFETY_ALERT|AWAITING_REFERRAL`) and frontend spec ("quick filters ... (single-select)") both call for a single active filter instead. We take this as an intentional replacement, not an oversight: the spec delta MODIFIES that requirement to single-select, and the frontend's `PrioritizationList.tsx` moves from five independent toggle buttons to the existing single-select `FilterChipRow` component (the same one already used by the Assessment Command Center's status/type rows and My Clients/Cases) — which also removes the earlier documented deviation ("quick filters are independent toggle buttons, not `FilterChipRow`, which is single-select-only") since a single-select filter is exactly what `FilterChipRow` is for. **BREAKING**: combining two quick filters (e.g. "Veterans" + "Safety Alerts") is no longer possible after this change.

## Risks / Trade-offs

- **The new scoring engine is still not clinically validated** → same mitigation the prior change used: a visible "provisional scoring model" disclosure in the UI (reusing the `HUD_WORKSPACE_DISCLOSURE_TEXT` treatment's pattern), and the real weights stay an explicit open item for the program team rather than something this change claims to finalize.
- **`Program` gains fields outside the original 5-model list the intake/case-workspace phases touched** → scoped to two nullable columns plus a seed backfill; flagged as an open item to confirm against the source org rather than treated as settled.
- **Adding `User.role` is a small step toward a permission system** → scoped strictly to the one `ce:manage-rules` check requested; no role-management UI or broader ACL ships in this change, avoiding a half-built RBAC surface.
- **Dropping `VulnerabilityAssessment` is breaking** → acceptable because no production data exists yet; any future change that needs to read old vulnerability-assessment data would need this change's git history, not a live table.
- **New Assessment form modal doesn't reuse the wizard's `assessmentDraft.ts` singleton** → slightly more state-management code (a second small hook) in exchange for avoiding a real collision risk the research surfaced; accepted rather than generalizing the singleton under time pressure.

## Migration Plan

1. Prisma migration: add `Assessment.assessorId/legacySyncStatus/legacySyncDate`, `ProgramEnrollment.endDate`, `Program.projectTypeCode/operatingOrganizationId`, `User.role`; create `program_exits`, `assessment_score_contributions`, `scoring_rules`, `care_plan_template_rules`, `ce_questions`, `ce_answer_options`, `ce_score_bands`, `ce_flag_overrides`, `ce_rule_changes`, `ce_assessments`, `ce_responses`; drop `VulnerabilityAssessment` and repoint `Referral`'s reverse relation.
2. Extend `prisma/seed.ts`: seed the provisional `scoring_rules` set, `care_plan_template_rules`, the 5 active `ce_questions`/answer options, 3 `ce_score_bands`, one `ce_flag_overrides` row per flag, `Program.projectTypeCode/operatingOrganizationId` backfill for the 5 existing seeded programs, and honor `SEED_USER_ROLE` (default `case_manager`) for the demo user.
3. Delete `apps/api/src/services/scoring.service.ts`; repoint its two call sites (`assessment.service.ts`, the old `coordinatedEntry.service.ts`) to the new services.
4. No rollback complexity beyond the standard "revert the migration + redeploy the prior archived change" — no production data is at stake.

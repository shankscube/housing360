## Standing rules for this repo

- **Never run `git commit` (or push) — the user commits their own work.** Don't ask for permission either; just leave changes in the working tree and, if useful, mention they're ready to commit.
- **Dev server hygiene**: if a dev server (`apps/api` and/or `apps/web`, or `turbo dev`) is already running when testing is needed, test against that one — don't start a second instance. If you start a server yourself for verification, stop it before ending the turn.
- `.env` holds real DB credentials. Never print its raw values (not even via `cat`/`xxd`/similar) — check presence/shape only (e.g. "is X set", key names, port reachability).
- **Parallelize with subagents by default.** Whenever work has independent, decomposable pieces — separate files/modules to build, separate areas to research, separate independent review dimensions — launch multiple Agent tool calls in a *single* message (true parallelism, not one-at-a-time), each with a self-contained brief and non-overlapping file ownership, rather than grinding through them serially in the main thread. Actively look for this opportunity before starting multi-part work, don't just fall back to serial by default. Only stay serial for tightly-coupled work, a single trivial edit, or steps where one genuinely depends on another's output.
- **All UI/frontend code lives in `apps/web` — never in a `packages/*` workspace package.** This was a deliberate call, made twice now (once during `project-setup`, reversed once during `base-components`, then corrected back): `apps/web` is the only consumer, so a separate `packages/ui` just adds workspace-package overhead (its own `package.json`, tsconfig, lint config, dependency wiring, Tailwind content-glob coordination) for zero actual sharing benefit. Reusable, screen-agnostic components (`KpiTile`, `StatusBadge`, etc.) belong in `apps/web/src/components/ui/`; the isolated component-preview tool belongs in `apps/web/ui-preview/`. Only pull UI code out into a `packages/` workspace if a second real consumer (another app, a design-system package published elsewhere, etc.) actually shows up — not preemptively "in case." If you're about to run `openspec new change` or otherwise plan work that touches shared components, route them through `apps/web`, not a new package.

## Structure

- `apps/web` — React 18, Vite, Tailwind, Redux Toolkit, TypeScript. Owns **all** UI/frontend code, including the shared component library (`src/components/ui/`) — see the standing rule above.
- `apps/api` — Node.js, Express, TypeScript, Prisma.
- `packages/types` — shared TS types/interfaces (`@housing360/types`), consumed by both apps.
- `packages/config` — shared ESLint (flat config), Prettier, and base `tsconfig` (`@housing360/config`).
- `docs/` — `Housing360 Portal.html` (note the space, not an underscore — approved design reference) and `prompts.md` (planning prompt sequence). Do not move/rename these.

## Backend conventions (apps/api)

- **Layering is enforced by lint, not just convention**: `routes/ → controllers/ → services/ → models/`. Only `services/` (and `models/` itself) may import from `models/`; this is a real ESLint rule (`packages/config/eslint/boundaries.js`, applied in `apps/api/eslint.config.js`), not just a folder-naming convention. Verified by deliberately breaking it during the original scaffold — it correctly failed lint.
- **No raw `res.json`/`res.send`/`res.end` outside `utils/responder.ts` and `middlewares/errorHandler.ts`** — also lint-enforced (same `boundaries.js`).
- **Response shape**: every endpoint goes through `src/utils/responder.ts` (`sendSuccess`/`sendError`) → `{ success, code, message, data }` or `{ success, code, message, errors }`. Controllers call `sendSuccess(...)` or `throw new AppError(...)` — they never build error responses inline. The centralized `src/middlewares/errorHandler.ts` is the only place failure responses get constructed.
- **Logging**: Pino + `pino-http` (`src/middlewares/requestLogger.ts`), structured, mounted before routes. Logs method/path/status/duration/request-id on every request. `no-console` is a lint error in this app.
- **Database**: MySQL via Prisma (default — see `src/config/database.ts` for the engine-detection logic that picks the engine from which `.env` vars are present; only MySQL is actually wired right now). Connection URL is assembled from `DB_HOST/PORT/USER/PASSWORD/NAME` in `.env`, never hardcoded, never logged. `src/config/loadEnv.ts` loads the **root** `.env` (not an `apps/api/.env`) via `dotenv`.
- **`prisma generate` runs via a `postinstall` script** in `apps/api/package.json` — required so a fresh `npm install` produces a working Prisma client before `dev`/`build` run. Don't remove this; without it, `turbo dev` crashes on first run after a fresh clone.
- `prisma/schema.prisma` has: the placeholder `AppMeta`; `User` — the single seeded case-manager demo user; and the client-domain models. **Every HUD-coded scalar field across these models (data-quality codes, veteran status, relationship-to-HoH, situation type, disability type, ...) is a plain `String`, never a Prisma enum** — `apps/api/src/constants/hudOptions.ts` is the one source of truth for code/label pairs (served verbatim from `GET /api/reference/hud-options`), and a Prisma enum would create a second one that needs a migration every time a code changes. Only `Sex` and `DisclosureStatus` stay real Prisma enums (small, fixed, predate this pattern).
  - `Client` — HUD Universal Data Elements plus intake-wizard fields: `firstName`/`lastName` (not a single `name` field), `title`, `nameDataQuality`/`ssnDataQuality`/`dobDataQuality`, `sex` enum, `raceEthnicity` (`Json`, an array of HUD codes — multi-value, not a single string), `mobile`/`email`, `veteranStatus` + veteran-detail columns (`militaryBranch`, `yearEnteredService`, `dischargeStatus`, `ww2`/`koreanWar`/`vietnamWar`/`otherTheater`), `householdId` (a real FK to `Household`, not a bare grouping string) + `relationshipToHoh` (HUD 3.15 — informational; see the `Household` bullet for what actually decides headship). SSN moved from a plain nullable column to **encrypted value + deterministic hash + last4**: `ssnEncrypted` (AES-256-GCM via `utils/ssn.ts`'s `encryptSsn`/`decryptSsn`), `ssnHash` (HMAC-SHA256 via `hashSsn`, keyed by a *separate* `SSN_HASH_SECRET` — never `SSN_ENCRYPTION_KEY` — used only for duplicate matching since GCM's random IV makes the same SSN encrypt differently every call), `ssnLast4` (via `lastFour`, for display). `ssnDisclosure`/`dob`/`dobDisclosure` keep the original disclosure-field pattern (value column + status enum) — DOB was never touched by the SSN-encryption change. Reuse `DisclosureField<T>`/`DisclosureStatus` from `packages/types/src/clients.ts` for any future sensitive field; reuse the SSN encrypt/hash/last4 pattern specifically for anything else that needs duplicate-matching without ever storing/returning a plaintext value.
  - `Household` — created *after* its head client already exists (`POST /api/households { clientId }`, in one transaction: creates the household with `headClientId = clientId`, then sets that client's `householdId`/`relationshipToHoh = '1'`). **The head is fixed at creation time — there is no "change head of household" endpoint.** Whether a client *is* the head is always `household.headClientId === client.id`; `relationshipToHoh` is informational metadata on every member (including the head) and is never the source of truth for headship. This structurally replaces the old `isHeadOfHousehold` boolean + service-layer single-head check — don't reintroduce either.
  - `Program` (seeded, 5 rows via `prisma/seed.ts`, not user-creatable — **gained `projectTypeCode` (`String?`, HUD 2.02 project-type code) and `operatingOrganizationId` (`String?`, FK `Organization`) in `assessment-and-ce-workspace`**, backfilled on the 5 seeded rows with placeholder values pending source-org confirmation; this is what Coordinated Entry's score-band → recommended-project-types → partner-program chain filters/joins on — the earlier note that "`Program` has no `type`/category column" no longer holds), `ProgramEnrollment` (gained `endDate`, `DateTime?`, set transactionally when an Exit assessment completes — see the `Assessment`/program-exit bullet below), `Case` — `clientId`+`programEnrollmentId`+`status` are unchanged from `client-intake-wizard` (`@@unique([clientId, programEnrollmentId])` so `POST /api/cases/ensure` is still a true idempotent upsert, Prisma compound key `clientId_programEnrollmentId`; its default `status` is still `'open'`, read as "Active" by the Cases screen — see below); `cases-screen` extended the row in place with `caseNumber` (server-generated `CASE-YYYY-NNNNN`, unique, never client-supplied — `case.model.ts`'s `generateCaseNumber`, count-based per year, not a DB sequence, with a one-time retry on a unique collision), `subject`, `priority` (`high`/`medium`/`low`, plain String per the HUD-coded-scalar convention below, not specific to HUD), `lastContactDate`, and `assignedCaseManagerId` (FK to `User`, nullable); `case-workspace` extended it again with `description`, `stage`/`origin` (both plain-String option lists resolved against `constants/caseWorkspaceOptions.ts`), `escalated` (Boolean), `contact`, `referralId` (FK to the new `Referral`, see below), `openedDate`/`closedAt`, `nextHmisReviewDue`/`hmisDataQualityStatus`, `followUpMilestone`/`followUpDueDate` (`none|30|60|90`, due date computed from the moment the reminder is set — see `case-workspace/design.md` Decision 2), and `createdById`/`updatedById` (FKs to `User`, populate the Overview tab's System Information block). `Assessment` (the Entry-stage — `dataCollectionStage = 1` by default — HUD assessment: Living Situation + Income/Benefits/Insurance + Health/DV all on one row; steps 4-6 of the intake wizard write to this ONE row, never a second — see below for how that guarantee survived this row growing recurrence support), `Disability` (child of `Assessment`, one row per disability, HIV-only fields populated only for that type), `InteractionSummary` (extended by `case-workspace` with `interactionPurpose`/`confidentialityType`/`partnerAccount`/`offering` and a polymorphic `relatedRecordType`/`relatedRecordId` pair). `assessments-and-coordinated-entry` extended `Assessment` in place — deliberately, not via a second colliding model/route family (see that change's `design.md` Decision 1) — with `type` (`entry|annual|exit`, kept in sync with `dataCollectionStage` by `constants/assessmentTypes.ts`'s `stageToAssessmentType`/`assessmentTypeToStage`; derived from the stage whenever a caller — the intake wizard included — doesn't pass one explicitly, so an Entry Assessment saved before this change still resolves to `type: 'entry'`), `dueDate`, `score`/`scoreLabel` (write-once, server-only — see `ScoringService` below; never accept these from a request body), and `cycleNumber` (`Int @default(1)`, changing the compound unique key to `@@unique([programEnrollmentId, dataCollectionStage, cycleNumber])`, Prisma key `programEnrollmentId_dataCollectionStage_cycleNumber` — every pre-existing call site never sets it, so it defaults to `1` and the Entry Assessment's "exactly one record" upsert guarantee is provably unchanged; it exists solely so an annual/exit assessment can recur across cycles/years without colliding with an earlier one on the same enrollment+stage). **`assessment-and-ce-workspace` added exactly 3 further columns**, per that change's Decision 1 (deliberately not touching `status`/`type`/`dueDate`/`score`/`scoreLabel`/`cycleNumber`, which are reused as-is): `assessorId` (`String?`, FK `User`, always set from `req.user.id` on every save and never accepted from the request body), `legacySyncStatus` (`String @default("not_synced")`, values `not_synced|pending|synced|failed`), `legacySyncDate` (`DateTime?`).

  - **The `HousingStabilityScoringService`/`CoordinatedEntryService` engines replace the deleted placeholder** (`assessment-and-ce-workspace`) — `apps/api/src/services/scoring.service.ts` (the old fixed-weight `scoreAssessment`/`scoreVulnerability` tally, explicitly marked PROVISIONAL) is gone, not deprecated in place. `HousingStabilityScoringService` (`apps/api/src/services/housingStabilityScoring.service.ts`) reads active `ScoringRule` rows (`field`, `matchValue` or `[rangeMin,rangeMax]`, `contribution`, `isActive` — seeded, still explicitly provisional, mirroring the old tally's factors so behavior doesn't regress), writes one `AssessmentScoreContribution` row per matching rule, sums into `Assessment.score`, and derives `scoreLabel` from the same band cutoffs the old placeholder used; `assessment.service.ts`'s `scoreIfCompleted()` calls it instead of the old service. **Known scoring gap**: disability-count-based scoring (the old placeholder had one) has no seeded `ScoringRule` row, since a `Disability` count can't be expressed as a single-field match — left for the scoring service to special-case via a computed pseudo-field, not yet done. `CoordinatedEntryService`/`apps/api/src/services/coordinatedEntryEngine.service.ts` replaces `scoreVulnerability`: sums `CeAnswerOption.score`, resolves the inclusive-range `CeScoreBand`, applies `CeFlagOverride`s in a **fixed evaluation order — Safety Alert → Veteran → Unaccompanied Youth** — and returns the recommended project types, applied overrides, and referral-suppression state (a triggered Safety Alert override sets `referralSuppressed: true` and carries its `externalReferralMessage` through). Neither engine's output (`Assessment.score`/`scoreLabel`, `AssessmentScoreContribution`, `CeAssessment.totalScore`/`bandId`) is ever client-suppliable — always computed server-side. Rule administration (CRUD for CE questions/answer options/score bands/flag overrides) is permission-gated (`ce:manage-rules`, see below) and has no admin UI yet — API only, a future Admin Panel phase.

This is deliberately minimal — no role-management UI, no multi-role-per-user, no scoped resource permissions — scoped strictly to this one check.

## Frontend conventions (apps/web)

- **One Redux Toolkit slice per domain** in `src/store/slices/` (auth, clients, cases, assessments, coordinatedEntry, dashboard, intake, carePlans, referrals, services) — no god slice. Combined in `src/store/index.ts`. `clients` is `{ list, detail }` only now — its old `intakeForm` sub-state (create-client/duplicate-candidate flow) moved to `intake` when `NewIntakeForm` was replaced by `IntakeWizard`; `clientsSlice` no longer has a `createClient` thunk. `cases` (`cases-screen`, extended by `case-workspace`) mirrors that same `{ list, detail }` shape — `list` also carries `kpis` (from the same `fetchCases` response, not a separate fetch); `detail` carries the selected `CaseDetail` plus its own `hudData`/`hudDataStatus`/`hudDataError` sub-state (a second, independent fetch — `GET /api/cases/:id/hud-data` isn't returned by the detail endpoint) and, since `case-workspace`, `interactionSummaries` (list/search/selected-detail) and `tasks` sub-state for the Overview tab. `carePlansSlice`/`referralsSlice`/`servicesSlice` (all `case-workspace`) are separate top-level slices rather than more `cases.detail` sub-state, since each has its own list-fetch/create/update lifecycle independent of which case is open (`referralsSlice` in particular also backs the Plan tab's partner-agency lookup, which isn't case-detail-shaped). Thunks call `apiClient.get/post/patch` directly, same as `clientsSlice` — no dedicated wrapper functions in `api/client.ts` for these domains (unlike `client-intake`'s endpoints, which do have named wrappers there). `intake` is the largest slice in the app: `phase` (`search|form|finished`), `currentStep`/`furthestStep`/`completedSteps` (**1-8, not 0-indexed** — matches the wizard's own "Step N of 8"), `ids` (client/household/case/enrollment/assessment/interactionSummary), `client` (the current client's full record, set on snapshot load or first successful save — lets any step read the client's name without a second fetch), and one sub-state object per domain (`search`, `snapshot`, `clientSave`, `household`, `programs`, `enrollments`, `assessment`, `disabilities`, `interactionSummary`, `hudOptions`). `saveClientBasicInfo` rejects with a `{kind:'duplicate', candidates} | {kind:'error', message}` discriminated union (via `rejectWithValue`) so step 1 can tell a 409 apart from a normal failure. Read `intakeSlice.ts` in full before touching any wizard step — it is the single source of truth for wizard state; don't build parallel local state for anything it already tracks. `assessments`/`coordinatedEntry` (both originally `assessments-and-coordinated-entry`, replacing the project-setup-era stub slices — the old `assessmentsSlice` fetched the wrong shape entirely, `coordinatedEntrySlice` called an endpoint that never existed; both then reworked again by `assessment-and-ce-workspace`) mirror the `{ list, detail }` and `{ per-step async sub-state }` shapes respectively: `assessments.list` carries `filter`/`typeFilter`/`kpis` alongside the usual pagination fields; `coordinatedEntry` has one `AsyncSlice<T>`-shaped sub-state per wizard step (`questions`/`assessment`/`recommendedPrograms`/`referral` — **`vulnerabilityAssessment`/`partnerAgencies` are gone, replaced by `questions`/`assessment` now that Step 1 is question-bank-driven and scores via `POST /api/ce/assessments`**) plus `priorityQueue` (**renamed from `prioritizationList`**: `items` + a **single** `filter: PriorityQueueFilterOption` (`'ALL' | PriorityQueueFilter`) + `search`, matching the now-single-select `GET /api/ce/priority-queue` contract — the 5 independently-toggleable quick-filter booleans described here previously no longer exist). `dashboard` (`home-dashboard`, replacing `project-setup`'s never-wired-up stub) is the simplest slice in the app: `{ home: HomeDashboardResponse | null, status, error }`, one `fetchHomeDashboard` thunk hitting `GET /api/dashboard/home` — no list/detail split, since the whole screen is one aggregate read. `HomeDashboardResponse`/`HomeKpiTile`/`HomeTaskItem`/`HomeDataQualityAlertItem` (`packages/types/src/dashboard.ts`) replaced the old placeholder `DashboardSummary` (`{ clientCount, caseCount }`) outright — nothing else imported it, so no migration shim was needed.
- **Single API client module**: `src/api/client.ts`. All thunks call through it — never `fetch` directly in a slice. It sends `credentials: 'include'` on every request so the auth cookie flows to `apps/api`.
- **Theme is single-sourced, and it is the *only* source**: `src/theme/tokens.ts` holds every design value extracted from `docs/Housing360 Portal.html` (colors, spacing, type scale, radii, shadows, letter-spacing, fixed layout measures). `src/theme/tailwindTheme.ts` builds the Tailwind `theme` block from it once and is imported by **both** `tailwind.config.ts` and `ui-preview/tailwind.config.ts`, so the preview can't drift. No file under `src/components/` may carry an inline hex, an arbitrary Tailwind value (`bg-[#…]`, `text-[10px]`), or a magic px number — if the design needs a value that isn't in `tokens.ts`, add it there, **named for its role** (`border-subtle`, `surface-muted`, `text-muted`), not its raw value. `tailwind.config.ts`'s `content` glob only needs `./src/**/*.{ts,tsx}` — since all UI code (including the shared component library) lives under `apps/web/src`, there's no cross-package glob to keep in sync.
- **The theme *overrides* `fontSize`, `borderRadius` and numeric `spacing` rather than extending them.** The design is **base-13px, not base-16px**; leaving Tailwind's defaults live would let an off-design value in behind a plausible-looking utility. A class that doesn't exist is a visible gap; a wrong-but-plausible one isn't. Sizes/radii were quantized from the bundle's 23 sizes and 12 radii — the mapping is commented in `tokens.ts`.
  - **Footgun this has already caused twice**: because `spacing` is *overridden*, Tailwind's default numeric width/height classes silently generate **nothing** — the scale stops at `24` (56px), so `w-56`, `w-72`, `h-32` etc. are dead classes that produce no CSS and no error. A dead `w-56` on a `<select>` next to a `flex-1` input is what squeezed the intake wizard's SSN box down to 30px. Width and height take their scale from `spacing`; `maxWidth` does *not* (it's in `extend`, so `max-w-4xl`/`max-w-6xl` are fine). If you need a fixed measure, add a named token to `layout` in `tokens.ts` (`wizardRail`, `fieldNarrow`, `kpiMinWidth`, …) and use `w-<tokenName>`. To check a class actually exists: `cd apps/web && npx tailwindcss -i src/index.css -o <tmpfile>` then grep the output for it — do **not** write to `/dev/null` on Windows, it creates a literal `nul` file that then breaks `turbo`'s file hashing.
- **Two fonts, self-hosted**: Inter (everything) and Lora (`font-display` — page titles, KPI numerals). Installed as `@fontsource-variable/inter` + `@fontsource/lora` and imported at the top of `src/index.css` (and `ui-preview/index.css`), so the app makes no external font request. The nav rail's wordmark is `public/housing360-logo.png`, extracted from the design bundle's own asset manifest.

Never hardcode a badge color at the call site.
- **`Icon`** (`src/components/ui/icons/`): `iconPaths.ts` holds the bundle's `ICON` map verbatim plus the icons it draws inline; `bell`, `settings` and the chevrons have no bundle counterpart and are drawn in the same idiom. Color is inherited via `currentColor` — set it with a text-color utility, don't pass a color in. Add new icons here rather than inlining SVG in a component.
- **`DataTable` owns its empty, loading, and pagination states** (`isLoading`, `emptyMessage`; loading wins when both apply) — screens should not hand-roll any of them. Columns support `numeric` (tabular figures) and `emphasis` (defaults to the first column, matching every table in the bundle). Pass an optional `pagination` prop (`{ page, pageSize, total, onPageChange }`) to get a `<tfoot>` range label + Prev/Next footer for free — added as a shared capability during `my-clients-screen`, not a My-Clients-only bolt-on; any future paginated table should use this rather than building its own footer.
- **`Button` is the only place that knows what a button looks like** (`src/components/ui/Button/`): **four variants** (a 4th, `danger`, was added by `assessment-and-ce-workspace` to back `ConfirmDialog`'s destructive-action styling — no danger/destructive button existed before) — `primary` (navy fill), `secondary` (teal fill), `tertiary` (outlined), `danger` — × two sizes — `md` (page-level, the bundle's New Intake / New Referral / New Case group) and `sm` (in-card, e.g. My Clients' table-card New Intake). It extends `ButtonHTMLAttributes`, defaults `type` to `"button"` so it can't accidentally submit a form, and owns the single disabled treatment. Never restyle a bare `<button>` — render this instead.
- **`PageHeader` actions render through `Button`**, so a page-header action and a standalone button of the same variant can't drift. `PageHeaderActionVariant` is an alias of `ButtonVariant`; `PageHeaderAction`'s shape is unchanged. `LoginPage`'s submit is a `Button` too.
- **Component preview tool**: `npm run ui-preview` in `apps/web` (Vite + Tailwind, port 6006) — a lightweight Storybook-equivalent gallery (`apps/web/ui-preview/`), a separate Vite root/build from the main app but still inside `apps/web`, not actual Storybook (kept intentionally light). Every component has a story under `ui-preview/stories/`. Its `tailwind.config.ts` imports the shared `../src/theme/tailwindTheme` (no duplicated palette or scale — safe now that it's all one package). Every story declares a `reference` naming the screen and section of `docs/Housing360 Portal.html` it mirrors, and the gallery header links the bundle, so parity is checked side by side rather than from memory. Two gotchas if you touch this: (1) Tailwind resolves relative `content` globs against `process.cwd()`, not the config file's own directory, and the npm script's cwd is `apps/web` not `ui-preview/` — that's why the globs are built from `__dirname` and `ui-preview/postcss.config.js` passes an explicit absolute `config` path to the `tailwindcss` plugin; (2) `apps/web/package.json` has `"type": "module"`, so any nested `.js` config file (like `ui-preview/postcss.config.js`) must use `export default`/`import`, not `module.exports`/`require` — apps/web's own root `postcss.config.js` already does this, follow that pattern.

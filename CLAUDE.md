## Standing rules for this repo

- **Never run `git commit` (or push) — the user commits their own work.** Don't ask for permission either; just leave changes in the working tree and, if useful, mention they're ready to commit.
- **Dev server hygiene**: if a dev server (`apps/api` and/or `apps/web`, or `turbo dev`) is already running when testing is needed, test against that one — don't start a second instance. If you start a server yourself for verification, stop it before ending the turn.
- `.env` holds real DB credentials. Never print its raw values (not even via `cat`/`xxd`/similar) — check presence/shape only (e.g. "is X set", key names, port reachability).
- **All UI/frontend code lives in `apps/web` — never in a `packages/*` workspace package.** This was a deliberate call, made twice now (once during `project-setup`, reversed once during `base-components`, then corrected back): `apps/web` is the only consumer, so a separate `packages/ui` just adds workspace-package overhead (its own `package.json`, tsconfig, lint config, dependency wiring, Tailwind content-glob coordination) for zero actual sharing benefit. Reusable, screen-agnostic components (`KpiTile`, `StatusBadge`, etc.) belong in `apps/web/src/components/ui/`; the isolated component-preview tool belongs in `apps/web/ui-preview/`. Only pull UI code out into a `packages/` workspace if a second real consumer (another app, a design-system package published elsewhere, etc.) actually shows up — not preemptively "in case." If you're about to run `openspec new change` or otherwise plan work that touches shared components, route them through `apps/web`, not a new package.

## What this repo is

Turborepo monorepo for the Housing360 rebuild: `apps/api` (Node/Express/TypeScript) + `apps/web` (React/Vite/TypeScript), sharing common packages. Scaffolded by the OpenSpec change `openspec/changes/archive/2026-09-22-project-setup/` (specs synced to `openspec/specs/project-scaffold/`). The full design-system pass — token extraction from the approved design reference, and every shared component plus the shell brought to visual parity with it — was `openspec/changes/archive/2026-09-23-design-system-implementation/` (specs synced into `openspec/specs/shared-ui/`; read its `design.md` open items before touching the rail's collapsed state, `KpiTile`, or the login screen). The shared app shell, reusable UI components, and minimal auth were added by `openspec/changes/archive/2026-09-22-base-components/` (specs synced to `openspec/specs/shared-ui/` and `openspec/specs/auth/`) — see that change's `proposal.md`/`design.md`/`specs/` for full rationale. Note: that change's own `design.md` argued for a separate `packages/ui` component package; that call was overridden after archiving — see the standing rule above — so `packages/ui` no longer exists. Trust the current spec/CLAUDE.md over that historical design doc. The first real domain entity and full-featured screen — `Client` (HUD Universal Data Elements, household grouping, the reusable disclosure-field pattern) plus the My Clients list/filter/intake screen — was added by `openspec/changes/archive/2026-09-23-my-clients-screen/` (specs synced to `openspec/specs/client-management/`); see that change's `design.md` for the disclosure-field-as-two-columns decision and the duplicate-check-then-confirm flow, and its `tasks.md` §11 for a set of layout/shared-component tweaks (nav-rail logout, `DataTable` pagination) applied directly from live user feedback after the initial apply.

## Structure

- `apps/web` — React 18, Vite, Tailwind, Redux Toolkit, TypeScript. Owns **all** UI/frontend code, including the shared component library (`src/components/ui/`) — see the standing rule above.
- `apps/api` — Node.js, Express, TypeScript, Prisma.
- `packages/types` — shared TS types/interfaces (`@housing360/types`), consumed by both apps.
- `packages/config` — shared ESLint (flat config), Prettier, and base `tsconfig` (`@housing360/config`).
- `docs/` — `Housing360 Portal.html` (note the space, not an underscore — approved design reference) and `prompts.md` (planning prompt sequence). Do not move/rename these.

## Backend conventions (apps/api)

- **Layering is enforced by lint, not just convention**: `routes/ → controllers/ → services/ → models/`. Only `services/` (and `models/` itself) may import from `models/`; this is a real ESLint rule (`packages/config/eslint/boundaries.js`, applied in `apps/api/eslint.config.js`), not just a folder-naming convention. Verified by deliberately breaking it during the original scaffold — it correctly failed lint.
- **No raw `res.json`/`res.send`/`res.end` outside `utils/responder.ts` and `middlewares/errorHandler.ts`** — also lint-enforced (same `boundaries.js`).
- **Response shape**: every endpoint goes through `src/utils/responder.ts` (`sendSuccess`/`sendError`) → `{ success, code, message, data }` or `{ success, code, message, errors }`. Controllers call `sendSuccess(...)` or `throw new AppError(...)` — they never build error responses inline. The centralized `src/middlewares/errorHandler.ts` is the only place failure responses get constructed.
- **Logging**: Pino + `pino-http` (`src/middlewares/requestLogger.ts`), structured, mounted before routes. Logs method/path/status/duration/request-id on every request. `no-console` is a lint error in this app.
- **Database**: MySQL via Prisma (default — see `src/config/database.ts` for the engine-detection logic that picks the engine from which `.env` vars are present; only MySQL is actually wired right now). Connection URL is assembled from `DB_HOST/PORT/USER/PASSWORD/NAME` in `.env`, never hardcoded, never logged. `src/config/loadEnv.ts` loads the **root** `.env` (not an `apps/api/.env`) via `dotenv`.
- **`prisma generate` runs via a `postinstall` script** in `apps/api/package.json` — required so a fresh `npm install` produces a working Prisma client before `dev`/`build` run. Don't remove this; without it, `turbo dev` crashes on first run after a fresh clone.
- `prisma/schema.prisma` has: the placeholder `AppMeta` (kept purely because Prisma refuses to generate a client with zero models); `User` — the single seeded case-manager demo user (`id`, `email`, `passwordHash`, `firstName`, `lastName`; no roles/permissions field — out of scope for this phase); and `Client` — the first real domain model. `Client` carries the HUD Universal Data Elements (`name`, `sex` enum, `raceEthnicity` as plain fields), `householdId` (a server-generated grouping key, **not** a foreign key to a separate `Household` table) + `isHeadOfHousehold`, and SSN/DOB as **disclosure fields**: a nullable value column (`ssn`/`dob`) plus a `<field>Disclosure` enum column (`PROVIDED | CLIENT_DOESNT_KNOW | PREFERS_NOT_TO_ANSWER | DATA_NOT_COLLECTED`). This value-column + status-enum-column pair is the reusable pattern for *any* future sensitive field (health status, domestic-violence history, ...) — don't invent a one-off representation for the next one; add the same two columns and reuse `DisclosureField<T>`/`DisclosureStatus` from `packages/types/src/clients.ts`. Cases, assessments, and coordinated-entry domain models still don't exist — that's future work.
- Endpoints so far: `GET /health` (live DB check via `SELECT 1`, success/`503`); `auth` mounted at `/auth` (not `/api/auth` — this app has no `/api` prefix, matching the `/health` precedent): `POST /auth/login`, `POST /auth/logout`, `GET /auth/me` (protected); and `client-management` mounted at **`/api/clients`** — the first (and so far only) `/api`-prefixed route group, a deliberate departure documented in `openspec/changes/archive/2026-09-23-my-clients-screen/design.md`, not an inconsistency to "fix": `GET /api/clients` (paginated list — filters `all|male|female|withProgram|withoutProgram|withCases|withoutCases` + free-text name search — list-safe fields only, **never** SSN/DOB), `GET /api/clients/:id` (full detail, including SSN/DOB), `POST /api/clients` (intake — see the duplicate-check bullet below), `PATCH /api/clients/:id`. All four are the first data routes behind `requireAuth` (previously only `/auth/me` used it) — SSN/DOB are real PII, so this was a deliberate call, not an oversight to revisit.
- **`POST /api/clients` doubles as its own duplicate-check endpoint** — there's no separate route for it. The service always checks name+DOB+SSN against existing clients first (only when both SSN and DOB were actually `provided`, not withheld); if matches exist and the request body doesn't set `confirmDuplicate: true`, it returns `{ status: 'duplicates_found', candidates }` (code 200) **without writing**; otherwise `{ status: 'created', client }` (code 201). The frontend calls this same endpoint twice — once implicit, once with confirmation — see `apps/web/src/routes/pages/clients/NewIntakeForm.tsx`.
- **Head-of-household is enforced in the service layer, not the database**: `client.service.ts`'s create/update reject (`AppError(409, ...)`) a second `isHeadOfHousehold: true` within the same `householdId` — MySQL has no native "exactly one true per group" constraint, so this only holds as long as writes go through the service. A `// TODO(household-duplicate-alert)` in `client.service.ts` marks a known, deliberately-unresolved gap: there is still no automated alert for a person registered in more than one household.
- **`filter=withProgram|withoutProgram|withCases|withoutCases` on `GET /api/clients` are contract-complete but currently trivial**: no `Program`/`Case` model exists yet, so `withProgram`/`withCases` always return zero rows and `withoutProgram`/`withoutCases` return every client. This is documented, expected behavior (see `client-management`'s spec/design), not a bug — revisit once those entities land.
- **SSN/DOB are never logged**: `src/utils/logger.ts`'s Pino `redact` config strips them from request-body logging (`req.body.ssn.value`, `req.body.dob.value`, and nested equivalents) — verified against a live server's actual log output, not just the config's presence. If you add another disclosure-capable field, extend the redact paths at the same time; it is not automatic.
- **Auth**: JWT in an httpOnly, `SameSite=Lax` cookie (name from `COOKIE_NAME` env var), not a client-visible token or server-side session store — see `openspec/changes/archive/2026-09-22-base-components/design.md` for why. `src/services/auth.service.ts` issues/verifies the JWT (bcrypt via `bcryptjs`, not native `bcrypt`, to avoid a node-gyp build step); `src/middlewares/auth.ts` (`requireAuth`) verifies the cookie on protected routes and populates `req.user`, 401-ing via `AppError`/`sendError` like any other layer — it does **not** bypass the responder convention. `apps/api/prisma/seed.ts` (`npm run seed` in `apps/api`, or `prisma db seed`) creates the one demo user from `SEED_USER_EMAIL`/`SEED_USER_PASSWORD`/`SEED_USER_FIRST_NAME`/`SEED_USER_LAST_NAME` env vars — never hardcoded. `cors` is configured with `credentials: true` and `origin` locked to `WEB_ORIGIN` (the Vite dev origin) so the cookie can flow cross-port in dev.
- The `AuthenticatedUser` shape is defined once in `packages/types/src/auth.ts` and imported by both apps — don't redefine it locally on either side.

## Frontend conventions (apps/web)

- **One Redux Toolkit slice per domain** in `src/store/slices/` (auth, clients, cases, assessments, coordinatedEntry, dashboard) — no god slice. Combined in `src/store/index.ts`. `clients` is the first slice with real sub-state rather than one flat bag: `{ list, detail, intakeForm }`, each with its own focused reducers and one thunk (`fetchClients`/`fetchClientById`/`createClient`) — follow this shape, not a single flat slice, the next time a domain outgrows one.
- **Single API client module**: `src/api/client.ts`. All thunks call through it — never `fetch` directly in a slice. It sends `credentials: 'include'` on every request so the auth cookie flows to `apps/api`.
- **Theme is single-sourced, and it is the *only* source**: `src/theme/tokens.ts` holds every design value extracted from `docs/Housing360 Portal.html` (colors, spacing, type scale, radii, shadows, letter-spacing, fixed layout measures). `src/theme/tailwindTheme.ts` builds the Tailwind `theme` block from it once and is imported by **both** `tailwind.config.ts` and `ui-preview/tailwind.config.ts`, so the preview can't drift. No file under `src/components/` may carry an inline hex, an arbitrary Tailwind value (`bg-[#…]`, `text-[10px]`), or a magic px number — if the design needs a value that isn't in `tokens.ts`, add it there, **named for its role** (`border-subtle`, `surface-muted`, `text-muted`), not its raw value. `tailwind.config.ts`'s `content` glob only needs `./src/**/*.{ts,tsx}` — since all UI code (including the shared component library) lives under `apps/web/src`, there's no cross-package glob to keep in sync.
- **The theme *overrides* `fontSize`, `borderRadius` and numeric `spacing` rather than extending them.** The design is **base-13px, not base-16px**; leaving Tailwind's defaults live would let an off-design value in behind a plausible-looking utility. A class that doesn't exist is a visible gap; a wrong-but-plausible one isn't. Sizes/radii were quantized from the bundle's 23 sizes and 12 radii — the mapping is commented in `tokens.ts`.
- **Two fonts, self-hosted**: Inter (everything) and Lora (`font-display` — page titles, KPI numerals). Installed as `@fontsource-variable/inter` + `@fontsource/lora` and imported at the top of `src/index.css` (and `ui-preview/index.css`), so the app makes no external font request. The nav rail's wordmark is `public/housing360-logo.png`, extracted from the design bundle's own asset manifest.
- **Vite reads the root `.env`** (not `apps/web/.env`) via `envDir: '../../'` in `vite.config.ts`. Frontend env vars must be prefixed `VITE_`.
- **App shell** (`src/components/layout/`): `AppShell.tsx` (nav rail + top bar + `<Outlet/>`, holds the collapse/expand state), `NavRail.tsx` (reads the static `navConfig.ts` item list — each top-level entry carries an `icon: IconName`; collapses to icon-only width with a width transition, and renders the bundle's bottom user card from `state.auth.currentUser`). That user card is clickable — it opens an account menu (currently just "Log out") portaled to `document.body` via `createPortal`, so the rail's own `overflow-hidden` (needed for the collapse transition) can't clip it; positioned at the icon's bottom-right, closes on outside click. `TopBar.tsx` has search/notifications/settings stubs + "Welcome, [First Name]" only, styled as the bundle's white `shadow-control` cards — **log out lives on the nav rail now, not here** (moved during `my-clients-screen` per direct user feedback on the running app). `ContentAreaTemplate.tsx` (page-title band → optional KPI row → content; every routed screen renders through this, built from `../ui`'s `PageHeader`/`KpiTile`, and passes an optional `subtitle` through). `useReferralsBadgeCount.ts` is a stub hook returning `0` until the Referrals module wires up real data. **Known gap**: because Insights and Tools are group headers with no route of their own, collapsing the rail hides them and their children entirely — see `openspec/changes/archive/2026-09-23-design-system-implementation/design.md`'s open items.
- **Auth-gated routing**: `src/routes/RouteGuard.tsx` wraps every screen route (real or stub) in `AppRoutes.tsx`; it dispatches `fetchCurrentUser` once on mount and redirects to `/login` (`src/routes/pages/LoginPage.tsx`) when unauthenticated. `/login` itself is the only route outside the guard.
- Stub screens: Home, Cases, Assessments, Coordinated Entry (`src/routes/pages/`) — each just mounts `ContentAreaTemplate`; business content is still future work. Everything else in the nav (Resource Directory, Referrals + Internal/Outbound, Shelter Management + Beds/Daily Log, Insights, Tools) is a `PlaceholderPage` route stub, wired in `AppRoutes.tsx`. **Don't use My Clients as a template for "just mount `ContentAreaTemplate`"** — use one of these instead; My Clients is the first screen with real business content (see below).
- **My Clients** (`src/routes/pages/MyClientsPage.tsx` + `src/routes/pages/clients/NewIntakeForm.tsx`) is the first fully-built screen: a `ContentAreaTemplate` (title + subtitle only, **no header actions** — New Intake is a `<Button variant="secondary" size="sm">` inside the table card's own header row, not a page-header action; that's the bundle's specific My Clients treatment, not the general pattern) wrapping one card — filter chips (`FilterChipRow`, single-select) + the New Intake button share one row, a full-width search input sits on its own row below that, then a caption strip, then `DataTable` with its `pagination` prop wired to the `clients` slice's `list` sub-state. There is **no column-visibility control** — an initial version had one; it was removed per direct user feedback right after the first apply. SSN and DOB columns render a fixed masked placeholder (`••••••••`), not a real last-4 mask: `ClientListItem` omits both fields from the list payload entirely by spec (never sent, not even masked), so there's no real value to mask without a per-row fetch against the detail endpoint — a future "reveal" action is the documented follow-up, not a bug to fix reflexively. The New Intake form runs the duplicate-check-then-confirm flow inline (an expand/collapse panel under the button — no shared `Modal` component exists yet, don't build one just for this) and uses a disclosure-field control (a real-value input plus a status select for the four disclosure states) for SSN and DOB.
- **`src/components/ui/` is the home for generic, screen-agnostic components** (`Icon`, `Button`, `KpiTile`, `StatusBadge`, `FilterChipRow`, `DataTable`, `PageHeader`, `StatusStepper`) — each in its own file, re-exported from `src/components/ui/index.ts` (and from `src/components/index.ts`). `src/components/layout/` stays for the app-specific shell (not generic/reusable elsewhere). Only add something to `src/components/ui/` if it has no screen-specific logic and a typed props interface — per the standing rule above, this directory is **not** a candidate for extraction into a `packages/*` workspace unless a genuine second consumer shows up.
- **`StatusBadge` resolves color in two steps, both centrally defined** (`src/components/ui/status/`): `statusToneByLabel.ts` maps a *status word* → tone (covering every word used across My Clients, Cases, Assessments and Coordinated Entry; unknown words fall back to `quiet`), and `statusColors.ts`'s `STATUS_COLOR_MAP` maps tone → fill/text classes. The six tones are the bundle's own vocabulary — `teal` (positive/active), `navy` (neutral-emphatic), `blue` (informational/in-progress), `gold` (waiting/due), `coral` (urgent/overdue/rejected), `quiet` (deemphasized) — **not** a four-step severity ramp; the navy/quiet and blue/gold distinctions carry real signal on the tables. Call sites pass only `label`; pass `tone` **only** where a word is domain-specific (the bundle renders "Enrolled" `teal` as a program status and `navy` as a referral stage). Never hardcode a badge color at the call site.
- **`Icon`** (`src/components/ui/icons/`): `iconPaths.ts` holds the bundle's `ICON` map verbatim plus the icons it draws inline; `bell`, `settings` and the chevrons have no bundle counterpart and are drawn in the same idiom. Color is inherited via `currentColor` — set it with a text-color utility, don't pass a color in. Add new icons here rather than inlining SVG in a component.
- **`DataTable` owns its empty, loading, and pagination states** (`isLoading`, `emptyMessage`; loading wins when both apply) — screens should not hand-roll any of them. Columns support `numeric` (tabular figures) and `emphasis` (defaults to the first column, matching every table in the bundle). Pass an optional `pagination` prop (`{ page, pageSize, total, onPageChange }`) to get a `<tfoot>` range label + Prev/Next footer for free — added as a shared capability during `my-clients-screen`, not a My-Clients-only bolt-on; any future paginated table should use this rather than building its own footer.
- **`Button` is the only place that knows what a button looks like** (`src/components/ui/Button/`): three variants — `primary` (navy fill), `secondary` (teal fill), `tertiary` (outlined) — × two sizes — `md` (page-level, the bundle's New Intake / New Referral / New Case group) and `sm` (in-card, e.g. My Clients' table-card New Intake). It extends `ButtonHTMLAttributes`, defaults `type` to `"button"` so it can't accidentally submit a form, and owns the single disabled treatment. Never restyle a bare `<button>` — render this instead.
- **`PageHeader` actions render through `Button`**, so a page-header action and a standalone button of the same variant can't drift. `PageHeaderActionVariant` is an alias of `ButtonVariant`; `PageHeaderAction`'s shape is unchanged. `LoginPage`'s submit is a `Button` too.
- **Component preview tool**: `npm run ui-preview` in `apps/web` (Vite + Tailwind, port 6006) — a lightweight Storybook-equivalent gallery (`apps/web/ui-preview/`), a separate Vite root/build from the main app but still inside `apps/web`, not actual Storybook (kept intentionally light). Every component has a story under `ui-preview/stories/`. Its `tailwind.config.ts` imports the shared `../src/theme/tailwindTheme` (no duplicated palette or scale — safe now that it's all one package). Every story declares a `reference` naming the screen and section of `docs/Housing360 Portal.html` it mirrors, and the gallery header links the bundle, so parity is checked side by side rather than from memory. Two gotchas if you touch this: (1) Tailwind resolves relative `content` globs against `process.cwd()`, not the config file's own directory, and the npm script's cwd is `apps/web` not `ui-preview/` — that's why the globs are built from `__dirname` and `ui-preview/postcss.config.js` passes an explicit absolute `config` path to the `tailwindcss` plugin; (2) `apps/web/package.json` has `"type": "module"`, so any nested `.js` config file (like `ui-preview/postcss.config.js`) must use `export default`/`import`, not `module.exports`/`require` — apps/web's own root `postcss.config.js` already does this, follow that pattern.

## Commands (from repo root)

```
npm install     # also runs apps/api's postinstall (prisma generate)
npm run dev       # turbo dev — both apps
npm run build      # turbo build
npm run lint        # turbo lint — includes the layering-boundary rule
npm run test          # turbo test
```

From `apps/api`: `npm run seed` seeds the one demo case-manager user (needs `SEED_USER_*` env vars set). From `apps/web`: `npm run ui-preview` serves the component preview gallery at `http://localhost:6006` (distinct from `npm run preview`, which is Vite's standard production-build preview).

Copy `.env.example` → `.env` at the repo root and fill in real values. Never commit `.env` (it's gitignored).

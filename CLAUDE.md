## Standing rules for this repo

- **Never run `git commit` (or push) — the user commits their own work.** Don't ask for permission either; just leave changes in the working tree and, if useful, mention they're ready to commit.
- **Dev server hygiene**: if a dev server (`apps/api` and/or `apps/web`, or `turbo dev`) is already running when testing is needed, test against that one — don't start a second instance. If you start a server yourself for verification, stop it before ending the turn.
- `.env` holds real DB credentials. Never print its raw values (not even via `cat`/`xxd`/similar) — check presence/shape only (e.g. "is X set", key names, port reachability).
- **Parallelize with subagents by default.** Whenever work has independent, decomposable pieces — separate files/modules to build, separate areas to research, separate independent review dimensions — launch multiple Agent tool calls in a *single* message (true parallelism, not one-at-a-time), each with a self-contained brief and non-overlapping file ownership, rather than grinding through them serially in the main thread. Actively look for this opportunity before starting multi-part work, don't just fall back to serial by default. Only stay serial for tightly-coupled work, a single trivial edit, or steps where one genuinely depends on another's output.
- **All UI/frontend code lives in `apps/web` — never in a `packages/*` workspace package.** This was a deliberate call, made twice now (once during `project-setup`, reversed once during `base-components`, then corrected back): `apps/web` is the only consumer, so a separate `packages/ui` just adds workspace-package overhead (its own `package.json`, tsconfig, lint config, dependency wiring, Tailwind content-glob coordination) for zero actual sharing benefit. Reusable, screen-agnostic components (`KpiTile`, `StatusBadge`, etc.) belong in `apps/web/src/components/ui/`; the isolated component-preview tool belongs in `apps/web/ui-preview/`. Only pull UI code out into a `packages/` workspace if a second real consumer (another app, a design-system package published elsewhere, etc.) actually shows up — not preemptively "in case." If you're about to run `openspec new change` or otherwise plan work that touches shared components, route them through `apps/web`, not a new package.

## Structure

- `apps/web` — React 18, Vite, Tailwind, Redux Toolkit, TypeScript. Owns **all** UI/frontend code, including the shared component library (`src/components/ui/`) — see the standing rule above.
- `apps/api` — Node.js, Express, TypeScript, Prisma.
- `packages/types` — shared TS types/interfaces (`@housing360/types`), consumed by both apps.
- `packages/config` — shared ESLint (flat config), Prettier, and base `tsconfig` (`@housing360/config`).
- `docs/` — `Housing360 Portal.html` (note the space, not an underscore — approved design reference) and `prompts.md` (planning prompt sequence). Do not move/rename these.

## Backend conventions (apps/api)

- **Layering is enforced by lint, not just convention**: `routes/ → controllers/ → services/ → models/`. Only `services/` (and `models/` itself) may import from `models/`; this is a real ESLint rule (`packages/config/eslint/boundaries.js`, applied in `apps/api/eslint.config.js`), not just a folder-naming convention. Verified by deliberately breaking it during the original scaffold — it correctly failed lint.
- **No raw `res.json`/`res.send`/`res.end` outside `utils/responder.ts` and `middlewares/errorHandler.ts`** — also lint-enforced (same `boundaries.js`).
- **Response shape**: every endpoint goes through `src/utils/responder.ts` (`sendSuccess`/`sendError`) → `{ success, code, message, data }` or `{ success, code, message, errors }`. Controllers call `sendSuccess(...)` or `throw new AppError(...)` — they never build error responses inline. The centralized `src/middlewares/errorHandler.ts` is the only place failure responses get constructed.
- **Logging**: Pino + `pino-http` (`src/middlewares/requestLogger.ts`), structured, mounted before routes. Logs method/path/status/duration/request-id on every request. `no-console` is a lint error in this app.
- **Database**: MySQL via Prisma (default — see `src/config/database.ts` for the engine-detection logic that picks the engine from which `.env` vars are present; only MySQL is actually wired right now). Connection URL is assembled from `DB_HOST/PORT/USER/PASSWORD/NAME` in `.env`, never hardcoded, never logged. `src/config/loadEnv.ts` loads the **root** `.env` (not an `apps/api/.env`) via `dotenv`.
- **`prisma generate` runs via a `postinstall` script** in `apps/api/package.json` — required so a fresh `npm install` produces a working Prisma client before `dev`/`build` run. Don't remove this; without it, `turbo dev` crashes on first run after a fresh clone.
- `prisma/schema.prisma` has: the placeholder `AppMeta`; `User` — the single seeded case-manager demo user; and the client-domain models. **Every HUD-coded scalar field across these models (data-quality codes, veteran status, relationship-to-HoH, situation type, disability type, ...) is a plain `String`, never a Prisma enum** — `apps/api/src/constants/hudOptions.ts` is the one source of truth for code/label pairs (served verbatim from `GET /api/reference/hud-options`), and a Prisma enum would create a second one that needs a migration every time a code changes. Only `Sex` and `DisclosureStatus` stay real Prisma enums (small, fixed, predate this pattern).
  - `Client` — HUD Universal Data Elements plus intake-wizard fields: `firstName`/`lastName` (not a single `name` field), `title`, `nameDataQuality`/`ssnDataQuality`/`dobDataQuality`, `sex` enum, `raceEthnicity` (`Json`, an array of HUD codes — multi-value, not a single string), `mobile`/`email`, `veteranStatus` + veteran-detail columns (`militaryBranch`, `yearEnteredService`, `dischargeStatus`, `ww2`/`koreanWar`/`vietnamWar`/`otherTheater`), `householdId` (a real FK to `Household`, not a bare grouping string) + `relationshipToHoh` (HUD 3.15 — informational; see the `Household` bullet for what actually decides headship). SSN moved from a plain nullable column to **encrypted value + deterministic hash + last4**: `ssnEncrypted` (AES-256-GCM via `utils/ssn.ts`'s `encryptSsn`/`decryptSsn`), `ssnHash` (HMAC-SHA256 via `hashSsn`, keyed by a *separate* `SSN_HASH_SECRET` — never `SSN_ENCRYPTION_KEY` — used only for duplicate matching since GCM's random IV makes the same SSN encrypt differently every call), `ssnLast4` (via `lastFour`, for display). `ssnDisclosure`/`dob`/`dobDisclosure` keep the original disclosure-field pattern (value column + status enum) — DOB was never touched by the SSN-encryption change. Reuse `DisclosureField<T>`/`DisclosureStatus` from `packages/types/src/clients.ts` for any future sensitive field; reuse the SSN encrypt/hash/last4 pattern specifically for anything else that needs duplicate-matching without ever storing/returning a plaintext value.
  - `Household` — created *after* its head client already exists (`POST /api/households { clientId }`, in one transaction: creates the household with `headClientId = clientId`, then sets that client's `householdId`/`relationshipToHoh = '1'`). **The head is fixed at creation time — there is no "change head of household" endpoint.** Whether a client *is* the head is always `household.headClientId === client.id`; `relationshipToHoh` is informational metadata on every member (including the head) and is never the source of truth for headship. This structurally replaces the old `isHeadOfHousehold` boolean + service-layer single-head check — don't reintroduce either.
  - `Program` (seeded, 5 rows via `prisma/seed.ts`, not user-creatable), `ProgramEnrollment`, `Case` — `clientId`+`programEnrollmentId`+`status` are unchanged from `client-intake-wizard` (`@@unique([clientId, programEnrollmentId])` so `POST /api/cases/ensure` is still a true idempotent upsert, Prisma compound key `clientId_programEnrollmentId`; its default `status` is still `'open'`, read as "Active" by the Cases screen — see below); `cases-screen` extended the row in place with `caseNumber` (server-generated `CASE-YYYY-NNNNN`, unique, never client-supplied — `case.model.ts`'s `generateCaseNumber`, count-based per year, not a DB sequence, with a one-time retry on a unique collision), `subject`, `priority` (`high`/`medium`/`low`, plain String per the HUD-coded-scalar convention below, not specific to HUD), `lastContactDate`, and `assignedCaseManagerId` (FK to `User`, nullable); `case-workspace` extended it again with `description`, `stage`/`origin` (both plain-String option lists resolved against `constants/caseWorkspaceOptions.ts`), `escalated` (Boolean), `contact`, `referralId` (FK to the new `Referral`, see below), `openedDate`/`closedAt`, `nextHmisReviewDue`/`hmisDataQualityStatus`, `followUpMilestone`/`followUpDueDate` (`none|30|60|90`, due date computed from the moment the reminder is set — see `case-workspace/design.md` Decision 2), and `createdById`/`updatedById` (FKs to `User`, populate the Overview tab's System Information block). `Assessment` (the Entry-stage — `dataCollectionStage = 1` by default — HUD assessment: Living Situation + Income/Benefits/Insurance + Health/DV all on one row; steps 4-6 of the intake wizard write to this ONE row, never a second — see below for how that guarantee survived this row growing recurrence support), `Disability` (child of `Assessment`, one row per disability, HIV-only fields populated only for that type), `InteractionSummary` (extended by `case-workspace` with `interactionPurpose`/`confidentialityType`/`partnerAccount`/`offering` and a polymorphic `relatedRecordType`/`relatedRecordId` pair). `assessments-and-coordinated-entry` extended `Assessment` in place — deliberately, not via a second colliding model/route family (see that change's `design.md` Decision 1) — with `type` (`entry|annual|exit`, kept in sync with `dataCollectionStage` by `constants/assessmentTypes.ts`'s `stageToAssessmentType`/`assessmentTypeToStage`; derived from the stage whenever a caller — the intake wizard included — doesn't pass one explicitly, so an Entry Assessment saved before this change still resolves to `type: 'entry'`), `dueDate`, `score`/`scoreLabel` (write-once, server-only — see `ScoringService` below; never accept these from a request body), and `cycleNumber` (`Int @default(1)`, changing the compound unique key to `@@unique([programEnrollmentId, dataCollectionStage, cycleNumber])`, Prisma key `programEnrollmentId_dataCollectionStage_cycleNumber` — every pre-existing call site never sets it, so it defaults to `1` and the Entry Assessment's "exactly one record" upsert guarantee is provably unchanged; it exists solely so an annual/exit assessment can recur across cycles/years without colliding with an earlier one on the same enrollment+stage). **Coordinated Entry now exists** — see the new `VulnerabilityAssessment` model and `coordinated-entry` endpoints below.
  - **`VulnerabilityAssessment`** (`assessments-and-coordinated-entry`) — Coordinated Entry's screening record, deliberately separate from `Assessment` (it can exist before a client has any `ProgramEnrollment`, which `Assessment.programEnrollmentId` requires). `answers` is a `Json` bag holding the placeholder VI-SPDAT-style intake shape (`VulnerabilityAssessmentInput` in `packages/types`) — a fixed column set isn't worth carving out before the real instrument is designed. `score`/`priorityTier` come from `ScoringService.scoreVulnerability`; `safetyAlert` is captured directly on the screening (can't depend on the intake wizard's `Assessment.domesticViolenceSurvivor` existing); `referralId` (nullable, unique) links to whichever `Referral` "Send Referral" creates, if the flow reaches step 4.
  - **`ScoringService`** (`apps/api/src/services/scoring.service.ts`, `assessments-and-coordinated-entry`) — `scoreAssessment`/`scoreVulnerability`, both a **clearly-labeled PROVISIONAL placeholder** (a small fixed-weight tally), explicitly not the real HUD housing-stability/VI-SPDAT algorithms — those are a future dedicated design pass. This is the only place `Assessment.score`/`scoreLabel` or `VulnerabilityAssessment.score`/`priorityTier` ever get computed; controllers never compute a score inline, and a client-supplied `score`/`scoreLabel` in a request body is always ignored (stripped server-side, not just untyped) rather than trusted.

`subtype` distinguishes the three without a second table. `CarePlanTemplate`/`CarePlanTemplateGoal`/`CarePlanTemplateTask` (seeded, not user-editable — `POST /api/care-plans` clones a template's goals/tasks as a one-time starting point, no live link back) and `GoalDefinition` (seeded suggested-goal catalog); `CarePlan`/`GoalAssignment` (goal tasks live in `Task` via `goalAssignmentId`, not a child table). `Benefit`/`BenefitAssignment` (**migrated in the Plan tab's own migration, not Services'** — Plan-tab service-gap detection needs `Benefit` to exist; `ServiceDisbursement`/`Bed`/`BedAssignment`/`BedNight` stayed in the Services-tab migration as planned — see `case-workspace/design.md` Decision 6's implementation note). `BedAssignment.shift` lives on the assignment itself, not only on `BedNight` — needed to tell apart a Day-shift and an Overnight-shift assignment to the same bed on the same date (see that design doc's Decision 9 note). `Referral`/`Organization`/`OrganizationServiceDomain` — one `Referral` table serves both the Referrals tab's internal CRUD and the Plan tab's ROI-gated external-referral path (`isExternal` plus which contact fields got populated is what tells them apart; `expiresOn` defaults to 365 days from signing. `ClinicalSummary`/`ClinicalEncounter` — a read model for the Health and Wellness tab that nothing writes to yet (see the `EhrAdapter` bullet below).

- **`GET /api/reference/hud-options`** serves `apps/api/src/constants/hudOptions.ts`'s `HUD_OPTIONS` map verbatim — the frontend fetches this once (`loadHudOptions` in `intakeSlice`) and renders every select/checkbox-group from it. **Never hardcode a HUD option list on the frontend** — if a list is missing a key, add it to `hudOptions.ts`, don't inline one.
- **`AppError` (`utils/AppError.ts`) carries an optional 4th `data` param**, threaded through by `utils/responder.ts`/`middlewares/errorHandler.ts` into the JSON error body's `data` field. This exists specifically so a thrown error can carry a structured payload (e.g. `POST /api/clients`' 409 duplicate-candidates response) while still going through the one `sendError` path — controllers still never build error responses inline, they just `throw new AppError(code, message, errors, data)`.

  All are behind `requireAuth`.
- **`POST`/`PATCH /api/clients`'s duplicate check is now HTTP 409, not 200 — an intentional break from the original `client-management` contract.** Matches on `firstName`+`lastName`+`dob`+`ssnHash` (never raw SSN) when both DOB and SSN are `provided` (not withheld); on a match without `allowDuplicate: true` in the body, throws `AppError(409, ..., [], { candidates })` — the wizard's step 1 renders this as an inline "Save Anyway" banner, not a toast. `confirmDuplicate` is gone; use `allowDuplicate`. The old `200 + { status: 'duplicates_found' }` shape no longer exists.
- **SSN/DOB/mobile/email/meetingNotes/nextSteps/description/notes/clientSignature/staffSignature are never logged**: `src/utils/logger.ts`'s Pino `redact` config strips all of them from request-body logging, including the wizard's `members[]` bulk-create array shape — verified against actual logger output, not just config presence. `description`/`notes` cover `case-workspace`'s free-text fields (Task description, Case description, referral/disbursement notes); `clientSignature`/`staffSignature` cover the ROI form's canvas-drawn signature data URLs. Extend the redact paths whenever a new PII-bearing field is added to a request body; it is not automatic.
- **Auth**: JWT in an httpOnly, `SameSite=Lax` cookie (name from `COOKIE_NAME` env var), not a client-visible token or server-side session store — see `openspec/changes/archive/2026-09-22-base-components/design.md` for why. `src/services/auth.service.ts` issues/verifies the JWT (bcrypt via `bcryptjs`, not native `bcrypt`, to avoid a node-gyp build step); `src/middlewares/auth.ts` (`requireAuth`) verifies the cookie on protected routes and populates `req.user`, 401-ing via `AppError`/`sendError` like any other layer — it does **not** bypass the responder convention. `apps/api/prisma/seed.ts` (`npm run seed` in `apps/api`, or `prisma db seed`) creates the one demo user from `SEED_USER_EMAIL`/`SEED_USER_PASSWORD`/`SEED_USER_FIRST_NAME`/`SEED_USER_LAST_NAME` env vars — never hardcoded. `cors` is configured with `credentials: true` and `origin` locked to `WEB_ORIGIN` (the Vite dev origin) so the cookie can flow cross-port in dev.
- The `AuthenticatedUser` shape is defined once in `packages/types/src/auth.ts` and imported by both apps — don't redefine it locally on either side.

## Frontend conventions (apps/web)

- **One Redux Toolkit slice per domain** in `src/store/slices/` (auth, clients, cases, assessments, coordinatedEntry, dashboard, intake, carePlans, referrals, services) — no god slice. Combined in `src/store/index.ts`. `clients` is `{ list, detail }` only now — its old `intakeForm` sub-state (create-client/duplicate-candidate flow) moved to `intake` when `NewIntakeForm` was replaced by `IntakeWizard`; `clientsSlice` no longer has a `createClient` thunk. `cases` (`cases-screen`, extended by `case-workspace`) mirrors that same `{ list, detail }` shape — `list` also carries `kpis` (from the same `fetchCases` response, not a separate fetch); `detail` carries the selected `CaseDetail` plus its own `hudData`/`hudDataStatus`/`hudDataError` sub-state (a second, independent fetch — `GET /api/cases/:id/hud-data` isn't returned by the detail endpoint) and, since `case-workspace`, `interactionSummaries` (list/search/selected-detail) and `tasks` sub-state for the Overview tab. `carePlansSlice`/`referralsSlice`/`servicesSlice` (all `case-workspace`) are separate top-level slices rather than more `cases.detail` sub-state, since each has its own list-fetch/create/update lifecycle independent of which case is open (`referralsSlice` in particular also backs the Plan tab's partner-agency lookup, which isn't case-detail-shaped). Thunks call `apiClient.get/post/patch` directly, same as `clientsSlice` — no dedicated wrapper functions in `api/client.ts` for these domains (unlike `client-intake`'s endpoints, which do have named wrappers there). `intake` is the largest slice in the app: `phase` (`search|form|finished`), `currentStep`/`furthestStep`/`completedSteps` (**1-8, not 0-indexed** — matches the wizard's own "Step N of 8"), `ids` (client/household/case/enrollment/assessment/interactionSummary), `client` (the current client's full record, set on snapshot load or first successful save — lets any step read the client's name without a second fetch), and one sub-state object per domain (`search`, `snapshot`, `clientSave`, `household`, `programs`, `enrollments`, `assessment`, `disabilities`, `interactionSummary`, `hudOptions`). `saveClientBasicInfo` rejects with a `{kind:'duplicate', candidates} | {kind:'error', message}` discriminated union (via `rejectWithValue`) so step 1 can tell a 409 apart from a normal failure. Read `intakeSlice.ts` in full before touching any wizard step — it is the single source of truth for wizard state; don't build parallel local state for anything it already tracks. `assessments`/`coordinatedEntry` (both `assessments-and-coordinated-entry`, replacing the project-setup-era stub slices — the old `assessmentsSlice` fetched the wrong shape entirely, `coordinatedEntrySlice` called an endpoint that never existed) mirror the `{ list, detail }` and `{ per-step async sub-state }` shapes respectively: `assessments.list` carries `filter`/`typeFilter`/`kpis` alongside the usual pagination fields; `coordinatedEntry` has one `AsyncSlice<T>`-shaped sub-state per wizard step (`vulnerabilityAssessment`/`recommendedPrograms`/`partnerAgencies`/`referral`) plus `prioritizationList` (`items` + the 5 independently-toggleable quick-filter booleans, composed as an AND when built into the request query string — never mutually exclusive).
- **Single API client module**: `src/api/client.ts`. All thunks call through it — never `fetch` directly in a slice. It sends `credentials: 'include'` on every request so the auth cookie flows to `apps/api`.
- **Theme is single-sourced, and it is the *only* source**: `src/theme/tokens.ts` holds every design value extracted from `docs/Housing360 Portal.html` (colors, spacing, type scale, radii, shadows, letter-spacing, fixed layout measures). `src/theme/tailwindTheme.ts` builds the Tailwind `theme` block from it once and is imported by **both** `tailwind.config.ts` and `ui-preview/tailwind.config.ts`, so the preview can't drift. No file under `src/components/` may carry an inline hex, an arbitrary Tailwind value (`bg-[#…]`, `text-[10px]`), or a magic px number — if the design needs a value that isn't in `tokens.ts`, add it there, **named for its role** (`border-subtle`, `surface-muted`, `text-muted`), not its raw value. `tailwind.config.ts`'s `content` glob only needs `./src/**/*.{ts,tsx}` — since all UI code (including the shared component library) lives under `apps/web/src`, there's no cross-package glob to keep in sync.
- **The theme *overrides* `fontSize`, `borderRadius` and numeric `spacing` rather than extending them.** The design is **base-13px, not base-16px**; leaving Tailwind's defaults live would let an off-design value in behind a plausible-looking utility. A class that doesn't exist is a visible gap; a wrong-but-plausible one isn't. Sizes/radii were quantized from the bundle's 23 sizes and 12 radii — the mapping is commented in `tokens.ts`.
  - **Footgun this has already caused twice**: because `spacing` is *overridden*, Tailwind's default numeric width/height classes silently generate **nothing** — the scale stops at `24` (56px), so `w-56`, `w-72`, `h-32` etc. are dead classes that produce no CSS and no error. A dead `w-56` on a `<select>` next to a `flex-1` input is what squeezed the intake wizard's SSN box down to 30px. Width and height take their scale from `spacing`; `maxWidth` does *not* (it's in `extend`, so `max-w-4xl`/`max-w-6xl` are fine). If you need a fixed measure, add a named token to `layout` in `tokens.ts` (`wizardRail`, `fieldNarrow`, `kpiMinWidth`, …) and use `w-<tokenName>`. To check a class actually exists: `cd apps/web && npx tailwindcss -i src/index.css -o <tmpfile>` then grep the output for it — do **not** write to `/dev/null` on Windows, it creates a literal `nul` file that then breaks `turbo`'s file hashing.
- **Two fonts, self-hosted**: Inter (everything) and Lora (`font-display` — page titles, KPI numerals). Installed as `@fontsource-variable/inter` + `@fontsource/lora` and imported at the top of `src/index.css` (and `ui-preview/index.css`), so the app makes no external font request. This cost real verification time during `case-workspace` (a whole session's worth of "passing" checks turned out to be vacuous, and only surfaced real errors once the actual build ran). To type-check `apps/web` for real, use `npx tsc -b tsconfig.json` (what `npm run build`'s `tsc -b && vite build` actually runs) or point directly at `npx tsc -p tsconfig.app.json --noEmit`. `apps/api`'s `tsconfig.json` is a normal (non-solution) config — `tsc -p tsconfig.json --noEmit` there is fine as-is.

Each of the 8 step components (`steps/Step1ClientBasicInfo.tsx` … `Step8InteractionSummary.tsx`) and the two phase components (`phases/SearchPhase.tsx`, `phases/FinishedPhase.tsx`) is self-contained, reading everything from `useAppSelector`/dispatching the `intake` slice's thunks directly — no props except `FinishedPhase`'s (`clientId`/`onViewClient`/`onDone`). **Steps 4 (Living Situation), 5 (Income & Benefits/Insurance), and 6 (Health & DV) share one module-level draft store** (`steps/assessmentDraft.ts`, `useSyncExternalStore`, *not* a `React.createContext` — survives each step unmounting with zero wiring in the shell) so step 6's "Save & Next" fires exactly one `saveEntryAssessment` call covering all three sections' fields, satisfying "steps 4-6 produce exactly one Entry Assessment record." `seedAssessmentDraftOnce(clientId, ...)` seeds it once per client id (resuming an existing assessment, or starting blank for a new client) without clobbering in-progress edits on back-navigation. **Known gap**: no generic Yes/No HUD option key exists server-side for fields without one of their own (most of steps 4-6's plain Yes/No fields) — they currently reuse `hudOptions.disablingCondition`'s Yes/No pair as a stand-in (`GENERIC_YES_NO_HUD_KEY` in `assessmentDraft.ts`); a real generic `yesNoDisclosure` HUD key is a documented follow-up.
- **`src/components/ui/` is the home for generic, screen-agnostic components** (`Icon`, `Button`, `KpiTile`, `StatusBadge`, `FilterChipRow`, `DataTable`, `PageHeader`, `StatusStepper`, `GatedField`, `DualListbox`, `StepRail`, `Toast`, `Tabs`, `Modal`, `ExpandableRow`, `SignaturePad`) — each in its own file, re-exported from `src/components/ui/index.ts` (and from `src/components/index.ts`). `src/components/layout/` stays for the app-specific shell (not generic/reusable elsewhere). Only add something to `src/components/ui/` if it has no screen-specific logic and a typed props interface — per the standing rule above, this directory is **not** a candidate for extraction into a `packages/*` workspace unless a genuine second consumer shows up.
- **`Modal`** (`src/components/ui/Modal/`, `case-workspace`): the first generic overlay/dialog primitive in the repo — `IntakeWizard` still hand-rolls its own `fixed inset-0` overlay (out of scope to refactor), but every new modal/wizard `case-workspace` added (New Case, Edit Case, the Care Plan wizard, Assign Service/Bed, disbursement/referral forms, the ROI form) renders through this one component instead. `{ isOpen, onClose, title, children, size? }`, portals to `document.body` (same technique as the nav rail's account menu), closes on Escape or a backdrop click.
- **`ExpandableRow`** (`src/components/ui/ExpandableRow/`, `case-workspace`): a single collapsible row (`{ summary, children, defaultExpanded? }`) — built once for the Plan tab's plan→goals→tasks nesting and the Services tab's enrollment→services→disbursements nesting, since both needed the identical pattern.
- **`SignaturePad`** (`src/components/ui/SignaturePad/`, `case-workspace`): a dependency-free canvas signature pad (`{ value, onChange, onClear, label? }`) — pointer events drawn to a fixed-resolution `<canvas>`, exported as a PNG data URL on pointer-up. Used twice per `ReleaseOfInformationForm` (client + staff signature).
- **`GatedField`** (`src/components/ui/GatedField/`): an unopinionated gate for one field against a declarative `{ targetField, sourceField, enablingValue }[]` rule list — pure props in (`rules`, `values`, `fieldName`), render-prop out (`children: (disabled, clear) => ReactNode`), no coupling to any form-state library. Multiple rules targeting the same field OR together. `onGateClose` fires once, internally, the instant a field's gate closes (`disabled` flips false→true) — wire your own clear logic there rather than writing that edge-detection effect yourself. This is what the Income & Benefits step (and any future step with a lot of Yes/No→Amount or No→Reason pairs) should use instead of hand-written conditionals — build ONE `rules` array for the whole step.
- **`DualListbox`** (`src/components/ui/DualListbox/`): two-column multi-select (available ↔ selected, click-to-highlight + arrow buttons or double-click to move, `chevronsRight`/`chevronsLeft` icons for move-all). Controlled via `{ options, selected, onChange }`. No bundle reference exists for this pattern (checked `docs/Housing360 Portal.html`) — it's a clean layout built from theme tokens, not a parity mirror. Used for Race and Ethnicity (multi-value HUD 3.04) in the intake wizard.
- **`StepRail`** (`src/components/ui/StepRail/`): renders `{key,label,icon?}[]` as upcoming/active/complete nodes, gated to `furthestStep`. **Indices are 0-based array positions**, not the `intake` slice's 1-8 step numbers — `IntakeWizard.tsx` converts (`currentStep - 1`, etc.) when calling it. The rail only renders the click-gate; "save the current step first" is the wizard shell's job in its `onStepClick` handler.
- **`Toast`** (`src/components/ui/Toast/`): a minimal, dependency-free toast queue — `ToastProvider` (mount once near the root of whatever feature needs it; `IntakeWizard`, `CasesPage`, and `CaseDetailPage` each do) + `useToast()` returning `{ showToast(message, tone?: 'error' | 'success') }`. `tone` defaults to `'error'` (unaffected pre-`case-workspace` call sites are all validation/failure messages); `'success'` renders teal/check instead of coral/alert, added by `case-workspace` for every create/update confirmation. Auto-dismisses after 4s or on click. Split across `ToastProvider.tsx` (component) and `ToastContext.ts` (context + hook) specifically so `react-refresh/only-export-components` stays happy — don't recombine them into one file.
- **`Tabs`** (`src/components/ui/Tabs/`, `cases-screen`): a generic tab strip — `{ tabs: {key,label}[], activeKey, onChange }`, styled from theme tokens only. It renders labels and the active-tab indicator and nothing else; it has no idea what any tab's panel contains — `CaseDetailPage` owns mounting the right panel for `activeKey`. Built here specifically because the Cases screen's 7-tab detail layout needed it and Assessments will likely want tabbed sections too — reuse this rather than building a second tab strip.
- **`StatusBadge` resolves color in two steps, both centrally defined** (`src/components/ui/status/`): `statusToneByLabel.ts` maps a *status word* → tone (covering every word used across My Clients, Cases, Assessments and Coordinated Entry; unknown words fall back to `quiet`), and `statusColors.ts`'s `STATUS_COLOR_MAP` maps tone → fill/text classes. The six tones are the bundle's own vocabulary — `teal` (positive/active), `navy` (neutral-emphatic), `blue` (informational/in-progress), `gold` (waiting/due), `coral` (urgent/overdue/rejected), `quiet` (deemphasized) — **not** a four-step severity ramp; the navy/quiet and blue/gold distinctions carry real signal on the tables. Call sites pass only `label`; pass `tone` **only** where a word is domain-specific (the bundle renders "Enrolled" `teal` as a program status and `navy` as a referral stage). Never hardcode a badge color at the call site.
- **`Icon`** (`src/components/ui/icons/`): `iconPaths.ts` holds the bundle's `ICON` map verbatim plus the icons it draws inline; `bell`, `settings` and the chevrons have no bundle counterpart and are drawn in the same idiom. Color is inherited via `currentColor` — set it with a text-color utility, don't pass a color in. Add new icons here rather than inlining SVG in a component.
- **`DataTable` owns its empty, loading, and pagination states** (`isLoading`, `emptyMessage`; loading wins when both apply) — screens should not hand-roll any of them. Columns support `numeric` (tabular figures) and `emphasis` (defaults to the first column, matching every table in the bundle). Pass an optional `pagination` prop (`{ page, pageSize, total, onPageChange }`) to get a `<tfoot>` range label + Prev/Next footer for free — added as a shared capability during `my-clients-screen`, not a My-Clients-only bolt-on; any future paginated table should use this rather than building its own footer.
- **`Button` is the only place that knows what a button looks like** (`src/components/ui/Button/`): three variants — `primary` (navy fill), `secondary` (teal fill), `tertiary` (outlined) — × two sizes — `md` (page-level, the bundle's New Intake / New Referral / New Case group) and `sm` (in-card, e.g. My Clients' table-card New Intake). It extends `ButtonHTMLAttributes`, defaults `type` to `"button"` so it can't accidentally submit a form, and owns the single disabled treatment. Never restyle a bare `<button>` — render this instead.
- **`PageHeader` actions render through `Button`**, so a page-header action and a standalone button of the same variant can't drift. `PageHeaderActionVariant` is an alias of `ButtonVariant`; `PageHeaderAction`'s shape is unchanged. `LoginPage`'s submit is a `Button` too.
- **Component preview tool**: `npm run ui-preview` in `apps/web` (Vite + Tailwind, port 6006) — a lightweight Storybook-equivalent gallery (`apps/web/ui-preview/`), a separate Vite root/build from the main app but still inside `apps/web`, not actual Storybook (kept intentionally light). Every component has a story under `ui-preview/stories/`. Its `tailwind.config.ts` imports the shared `../src/theme/tailwindTheme` (no duplicated palette or scale — safe now that it's all one package). Every story declares a `reference` naming the screen and section of `docs/Housing360 Portal.html` it mirrors, and the gallery header links the bundle, so parity is checked side by side rather than from memory. Two gotchas if you touch this: (1) Tailwind resolves relative `content` globs against `process.cwd()`, not the config file's own directory, and the npm script's cwd is `apps/web` not `ui-preview/` — that's why the globs are built from `__dirname` and `ui-preview/postcss.config.js` passes an explicit absolute `config` path to the `tailwindcss` plugin; (2) `apps/web/package.json` has `"type": "module"`, so any nested `.js` config file (like `ui-preview/postcss.config.js`) must use `export default`/`import`, not `module.exports`/`require` — apps/web's own root `postcss.config.js` already does this, follow that pattern.

## Environment

Copy `.env.example` → `.env` at the repo root and fill in real values. Never commit `.env` (it's gitignored). See `.env.example` for the full documented variable list — now includes `JWT_SECRET`/`JWT_EXPIRES_IN`/`COOKIE_NAME`/`WEB_ORIGIN` (auth), `SEED_USER_*` (seed script only, not used by the running app), and `SSN_ENCRYPTION_KEY`/`SSN_HASH_SECRET` (32-byte hex, `apps/api/src/utils/ssn.ts` — two *separate* keys, never reuse `JWT_SECRET`; the app fails to start if either is unset, same as `DB_*`).
